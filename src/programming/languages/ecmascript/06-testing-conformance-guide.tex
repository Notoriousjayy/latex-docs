\section{Testing objectives and conformance boundaries}\label{testing-objectives-and-conformance-boundaries}

This testing guide separates (1) ECMAScript engine conformance, (2) host interoperability, and (3) application correctness/security. \textbf{{[}SPEC{]}} conformance follows ECMA-262:2025 clause 2 and the language algorithms. \textbf{{[}HOST{]}} covers file loading, browser APIs, Node features, and scheduling outside the full language contract. \textbf{{[}TEST{]}} denotes a suggested test technique or release gate, not a requirement of ECMA-262.

\textbf{Official conformance corpus:} TC39's Test262 (https://github.com/tc39/test262) tests observable requirements across ECMA-262 and related Ecma standards. Its scope is broad but not exhaustive; a green suite is evidence, not a mathematical proof of conformance. Test262 runner integration and supported features must be configured appropriately.

\section{Test262 adoption workflow}\label{test262-adoption-workflow}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Pin an identified Test262 revision and record the ECMAScript edition/features being evaluated.
\item
  Select a maintained runner for the target engine; follow Test262 \passthrough{\lstinline!INTERPRETING.md!} for metadata flags and harness semantics.
\item
  Partition test cases by parse goal, feature tags, and applicability (e.g., host-limited or unsupported features).
\item
  Establish baseline: tests passed, skipped with rationale, expected fails, unexpected fails, harness failures.
\item
  Triage discrepancies using source clause algorithms and independently reproduce in a minimal script.
\item
  Regression-test confirmed defects; preserve crash dumps or engine diagnostic traces where appropriate.
\item
  Record suite version, command, engine build, and environment in the conformance report.
\end{enumerate}

\textbf{{[}TEST{]}} Avoid labeling unsupported host APIs as engine-language failures. Conversely, a skipped ECMAScript 2025 feature means the engine cannot be claimed fully conformant to that edition without qualification. Use exception labels as explicit evidence instead of silently suppressing failures.

\section{Unit-test starter: deterministic language behavior}\label{unit-test-starter-deterministic-language-behavior}

The following Node.js \passthrough{\lstinline!node:test!}/\passthrough{\lstinline!node:assert/strict!} example uses host tooling for assertions but checks language-defined semantics. It is not a Test262 replacement.

\begin{lstlisting}
// semantics.test.mjs (Node.js example)
import test from 'node:test';
import assert from 'node:assert/strict';

test('strict equality and signed zero', () => {
  assert.equal(0 === -0, true);
  assert.equal(Object.is(0, -0), false);
});

test('Map uses SameValueZero for NaN keys', () => {
  const map = new Map([[NaN, 'stored']]);
  assert.equal(map.get(Number.NaN), 'stored');
});

test('lexical temporal dead zone', () => {
  assert.throws(() => { void x; let x = 1; }, ReferenceError);
});
\end{lstlisting}

\section{ECMAScript 2025 API tests}\label{ecmascript-2025-api-tests}

\begin{lstlisting}
// Run only where ECMAScript 2025 features are supported.
const t = [1, 2, 3, 4][Symbol.iterator]().filter(x => x > 2).toArray();
console.assert(t.join(',') === '3,4');

const left = new Set(['a', 'b']);
const right = new Set(['b', 'c']);
console.assert(left.symmetricDifference(right).has('a'));
console.assert(left.isDisjointFrom(new Set(['c'])));

console.assert(new RegExp(RegExp.escape('a+b')).test('a+b'));
Promise.try(() => { throw new RangeError('x'); })
  .then(() => { throw new Error('unexpected fulfillment'); }, e => {
    console.assert(e instanceof RangeError);
  });

const half = new Float16Array([0.1]);
console.assert(half[0] === Math.f16round(0.1));
\end{lstlisting}

\textbf{{[}TEST{]}} For every API above include receiver validation, empty input, abrupt completion, method override/side effect, and cross-realm behavior where relevant. Do not use feature existence alone as proof of semantic conformance.

\section{Property-based and metamorphic tests}\label{property-based-and-metamorphic-tests}

\textbf{{[}TEST{]}} Generate inputs across classes and verify algebraic relations. For finite sets, intersection is a subset of both operands; symmetric difference membership is exclusive-or. For any string \passthrough{\lstinline!s!}, \passthrough{\lstinline!new RegExp(RegExp.escape(s), 'u')!} must match a direct occurrence of \passthrough{\lstinline!s!} within a compatible input, subject to deliberate test framing (regex flags and Unicode representation matter). For \passthrough{\lstinline!Math.f16round!}, applying twice should be idempotent on valid numeric inputs, with careful \passthrough{\lstinline!NaN!}/signed-zero assertions.

\begin{lstlisting}
function assertSetIdentity(a, b) {
  const left = a.intersection(b);
  for (const value of left) {
    if (!a.has(value) || !b.has(value)) throw new Error('intersection bug');
  }
  if (a.union(b).size < Math.max(a.size, b.size))
    throw new Error('union cardinality bug');
}
\end{lstlisting}

\section{Negative and exception testing}\label{negative-and-exception-testing}

\textbf{{[}SPEC{]}} A \passthrough{\lstinline!throw!} completion is observably different from a normal \passthrough{\lstinline!undefined!} result. Write tests for syntax errors that occur during parse, runtime errors during evaluation, and rejected promises after resolution. Keep test expectations precise: error type, timing, and object identity where defined; message text is often not standardized.

\begin{lstlisting}
const problem = new Error('expected');
const p = Promise.try(() => { throw problem; });
await p.then(
  () => { throw new Error('must reject'); },
  actual => { if (actual !== problem) throw new Error('wrong reason'); }
);
\end{lstlisting}

\section{CI conformance gate and triage}\label{ci-conformance-gate-and-triage}

\textbf{{[}TEST{]}} Suggested quality gate: build and parse checks; fast deterministic unit tests; security regression tests; compatibility jobs on supported runtime versions; targeted Test262 suites for engine implementers. Preserve failure artifacts. Classify failures as (a) source error, (b) host dependency, (c) unsupported feature, (d) runner/harness failure, or (e) conformance candidate. Only class (e), after reproduction, should be escalated as a potential specification implementation defect.

\section{Release verification checklist}\label{release-verification-checklist}

\begin{itemize}
\tightlist
\item[$\square$]
  Identified exact ECMA-262 edition and applicable clauses.
\item[$\square$]
  Explicitly listed 2025 feature support for each target.
\item[$\square$]
  Distinct parse, runtime, built-in, host, and application test layers.
\item[$\square$]
  Captured positive, negative, boundary, and abrupt-completion cases.
\item[$\square$]
  Validated test harness/runner semantics and pinned versions.
\item[$\square$]
  Examined skips, expected failures, and inconsistent engines rather than hiding them.
\item[$\square$]
  Traced every security regression test to a reachable threat scenario.
\item[$\square$]
  Archived executable commands and evidence of pass/fail decisions.
\end{itemize}
