A guideline \emph{headline} alone is not a complete compliance test. The source's Section~3 defines classifications, categories, decidability, analysis scope, and applicability.\par

\section{Reference architecture and bounded claims}
A reproducible MISRA workflow compiles the exact product configuration, invokes an appropriately validated C++17 checker, records rule mapping and coverage, validates dispositions, and archives evidence. GitHub code scanning is a distribution and triage interface for SARIF; an imported SARIF alert is not a substitute for MISRA guideline adjudication or a claim of compliance.

External context verified against GitHub documentation at https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/integrate-with-existing-tools/upload-sarif-file (consulted 16 Oct 2026). It documents github/codeql-action/upload-sarif@v4 and analysis category identifiers for multiple scans. Vendor support, entitlements and project permissions still must be confirmed.

\section{GitHub Actions workflow template}
The following example deliberately fails if a project-specific MISRA analyzer is absent. It cannot be executed as-is in an arbitrary repository; the analyzer wrapper, coverage generator, authorization data and CMake target must be supplied. It is a scaffold, not a zero-configuration compliant toolchain.

\begin{lstlisting}[language={},caption={Proposed workflow; also provided at templates/misra-cpp.yml}]
# EXAMPLE ONLY. Requires vendor MISRA checker and authoritative coverage validation.
# NOT a compliance certification or a working scanner without project setup.
name: MISRA C++17 review (template)
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  misra-cpp17:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/checkout@v6
      - name: Generate actual compilation database
        run: cmake -S . -B build -DCMAKE_CXX_STANDARD=17 -DCMAKE_EXPORT_COMPILE_COMMANDS=ON && cmake --build build
      - name: Run configured MISRA analyzer
        run: |
          # Replace with your licensed / validated analyzer invocation.
          # It must generate findings.json, coverage.json and vendor.sarif.
          test -x tools/run-project-misra-analyzer || exit 2
          tools/run-project-misra-analyzer --compdb build/compile_commands.json \
            --findings findings.json --coverage coverage.json --sarif vendor.sarif
      - name: Evaluate category, approval, and coverage policy
        run: python3 scripts/evaluate_misra_gate.py --catalog data/guidelines.csv --findings findings.json --coverage coverage.json
      - name: Upload tool SARIF
        if: always()
        uses: github/codeql-action/upload-sarif@v4
        with:
          sarif_file: vendor.sarif
          category: misra-cpp17-vendor
\end{lstlisting}

\section{Category-aware policy gate}
The sample Python policy gate reads data/guidelines.csv and two project-generated JSON files. It enforces presence of all 179 coverage records (machine-supported or explicitly manual-reviewed) and rejects unhandled Mandatory, Required, or Advisory findings. It does not verify that a stated resolution/approval was authentic; an independent source-control and evidence-review system must do so. The example is included as scripts/evaluate\_misra\_gate.py.

Do not map SARIF severities directly to MISRA categories. They are different taxonomies. Keep source guideline ID and compliance disposition in custom structured properties, while using SARIF tool metadata to maintain precise code navigation.

\begin{lstlisting}[language=bash,caption={Gate invocation after vendor analysis}]
python3 scripts/evaluate_misra_gate.py \
  --catalog data/guidelines.csv \
  --findings findings.json \
  --coverage coverage.json
\end{lstlisting}

\section{Pull-request merge strategy}
\begin{itemize}
\item Require successful complete-build-variant checks and human approvals on designated branches.
\item Never infer a fixed MISRA violation solely from a merged patch or an empty Code Scanning page; rescans must run on the actual target configuration.
\item Require an analyzer or reviewed manual evidence for directives and coverage gaps.
\item Set release blocking by policy status and source category, not by a generic SARIF severity filter.
\item Avoid privileged secrets in untrusted fork pull-request analysis; use isolated runners and follow GitHub Actions permission hardening.
\item Use unique SARIF categories for distinct vendor/variant streams, and keep stable fingerprints to preserve alert identity.
\end{itemize}

\section{Supply-chain and audit considerations}
Pin or approve action versions under repository policy; restrict GITHUB\_TOKEN scopes; log all third-party analyzer licenses and versions; preserve the exact source revision, compiler runtime and approved deviation approvals. Ensure generated code and precompiled headers are represented in the analysis context.

Keep tool findings separate from the declaration itself. A formal software item compliance assessment should reference the artifact manifest, guideline coverage map, technical residual risks and independent approval record.
