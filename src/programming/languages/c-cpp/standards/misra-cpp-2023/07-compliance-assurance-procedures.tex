\section*{How to read normative status}\addcontentsline{toc}{section}{How to read normative status}
\textbf{Normative source:} the licensed MISRA C++:2023 guideline text, including any applicable \emph{Amplification} and \emph{Exception}. A guideline \emph{headline} alone is not a complete compliance test. The source's Section~3 defines classifications, categories, decidability, analysis scope, and applicability.\par
\textbf{Independent guidance:} all review questions, programming patterns, lifecycle processes, sample thresholds, ownership assignments, controls, and CI configurations in this suite are \emph{engineering recommendations}, not statements issued by MISRA.\par
\textbf{Critical limitation:} no individual example is asserted compliant with the whole standard. For formal compliance claims, follow the applicable edition of \emph{MISRA Compliance} as the source itself instructs, with a documented compliance plan and supporting evidence.\par

\section{Governance assumptions and hierarchy}
The authoritative source requires following the current edition of MISRA Compliance when making a compliance claim (MISRA C++:2023 Section 1.5). That separate publication was not provided. The following forms and workflows are proposed implementation templates and must be reviewed against the applicable MISRA Compliance publication, customer requirements and internal assurance standard before any formal declaration.

Normative categories must remain unchanged in any derived governance layer: Mandatory forbids deviations; Required needs formal deviations for actual violations; Advisory requires either adherence or documented justification. A project may apply stronger categories only through controlled policy.


\section{SOP-01: Baseline and scope approval}
\begin{enumerate}
\item Identify executable units, software item and subsystem boundaries, third-party code, generated code, excluded source, build artifacts and all shipping variants.
\item Freeze compiler and C++17 standard mode, target ABI, dependencies, libraries, generator settings and preprocessor definitions in a baseline artifact.
\item Cross-reference all source guideline IDs, design directives and static-checker mappings, including partial/unsupported items.
\item Record applicable software lifecycle standard and independent-review requirement.
\item Obtain owner signoff and publish a version-controlled plan before claiming analysis completeness.
\end{enumerate}

\section{SOP-02: Static analysis and code review}
\begin{enumerate}
\item Produce a reproducible build manifest and compile database using the exact target toolchain.
\item Run the qualified project checks on all included translation units and execute System-scope analyses with their required source context.
\item Run testing/verification activities independent of static analysis and capture results.
\item Triage each finding to exact source ID and affected build configuration.
\item For source-defined exceptions, attach the qualifying semantic proof; do not create a deviation unless a true violation exists.
\item For undecidable rules, record why a path is or is not feasible; mark unresolved analysis limitations separately.
\item Require independent reviewer approval for findings likely to affect safety, memory safety or critical interfaces.
\end{enumerate}

\section{SOP-04: Deviation review}
\begin{enumerate}
\item Check that the ID is not Mandatory; confirm the source-defined exception does not already cover the use.
\item Provide rule ID, exact occurrence, operational need, alternative design options and failure mode impact.
\item Record compensating controls, residual risk, tests, independent reviewer and approval scope.
\item Approve only bounded files/configurations/releases, and set review triggers such as compiler change or new analyzer detection.
\item Reassess deviations at each release and when source/target code changes; close expired requests.
\end{enumerate}

\section{SOP-05: Release assurance}
\begin{enumerate}
\item Reconcile shipped binary inputs with analyzed inputs and source baseline.
\item Ensure all Mandatory violations are resolved and all Required actual violations have corrective evidence or valid formal deviations.
\item Ensure all Advisory violations are either resolved or have documented reasons; justify any project disapplication.
\item Collect analyzed build logs, test outputs, peer review record, tool-coverage gaps, deviations and documented uncertainties.
\item Have the designated authority review unresolved assumptions, third-party boundaries and the product claim wording.
\item Issue only a scoped, evidence-backed compliance statement; archive data with the released configuration.
\end{enumerate}

\section{Assurance review questions}
\begin{itemize}
\item Did the review examine the source guideline's amplification and exceptions?
\item Is every analysis assumption connected to an analyzed shipping configuration?
\item Can every deviation be found by guideline ID, source location and release?
\item Are source-defined exceptions distinguished from sanctioned violations?
\item Is the scope of the compliance claim narrower than or equal to the evidence scope?
\end{itemize}
