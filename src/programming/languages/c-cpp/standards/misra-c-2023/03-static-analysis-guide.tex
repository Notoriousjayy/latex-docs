\section{Verification model}
Static analysis is one component of compliance evidence, not the complete process. The enforcement plan should map every applicable guideline to a method: compiler diagnostic, syntax-based checker, semantic analyzer, whole-program dataflow, manual design review, proof, runtime testing, or an engineered combination. For each method record configuration, tool version, scope, checker IDs, positive/negative validation examples and known gaps.
\section{Coverage dimensions}
\begin{itemize}
\item \textbf{Guideline coverage}: what the tool claims to check for the exact revision; do not inherit 2012 claims into 2023 without validation.
\item \textbf{Analysis scope}: unit-level checks versus cross-translation-unit whole-program semantics and linked libraries.
\item \textbf{Decidability}: theoretical property of the rule; real analyzer soundness/completeness may be weaker.
\item \textbf{Language and target}: selected C edition, compiler extensions, preprocessor symbols, word widths, ABI, library and optimizer assumptions.
\item \textbf{Diagnostic quality}: true violations, false positives, missed findings, duplicates, environment errors and manual-review obligations.
\end{itemize}
\begin{keybox}\textbf{Do not compute compliance as} one minus open alerts divided by total alerts. That number omits rules the tool never checked, paths the engine could not prove, unanalyzed build configurations, excluded source and suppliers.\end{keybox}
\section{Evidence-oriented pipeline}
\begin{enumerate}
\item Select language edition, hardware model, required compiler flags and all supported build configurations.
\item Generate a compile database or equivalent source and option inventory. Include generated and third-party code boundaries.
\item Execute compiler and analyzer checks with fixed, reviewable versions and full logs.
\item Perform interprocedural/system checks on complete linked sources or record their evidence boundary.
\item Normalize findings by guideline ID, tool rule ID, file range, fingerprint, configuration and severity.
\item Triage with independent reviewer for undecidable or uncertain diagnostics; retain reproducible rationale.
\item Cross-reference findings to required deviations and correction commits; confirm remediation with reanalysis.
\item Export a final signed or controlled evidence packet into the compliance dossier.
\end{enumerate}

\section{Diagnostic triage decision tree}
\begin{enumerate}
\item \textbf{Is the run trustworthy?} Verify success, complete compilation and no missing translation units. If not, repair the analysis setup.
\item \textbf{Does the rule apply?} Check edition, exception, project scope and generated-code treatment against the licensed text.
\item \textbf{Is the behavior real?} Examine call paths, macro expansions, aliasing, range and external dependencies; classify uncertain undecidable findings distinctly.
\item \textbf{Can it be corrected safely?} Change code, re-run requirements tests and tool checks, or seek a formal deviation where allowed.
\item \textbf{Is evidence sufficient?} Record the reviewer, analysis inputs, reasoning, location and follow-up state.
\end{enumerate}
\section{Acceptance criteria for a tool purchase}
Demand: a versioned 2023 guideline map; list of not-covered rules and directives; exact C profile support; cross-TU support; verification corpus; APIs/exports; false-positive reduction; traceability; change-management workflow; and documented support for code generators, inline assembly and compiler-specific libraries. Challenge vendor ``100\% MISRA'' marketing unless the coverage definition is independently specified.
