\section{Review questions before a pull request}
\begin{enumerate}
\item Is there a requirement for this behavior and a test for failure behavior?
\item Are input ranges, buffer extents, pointer validity and output contracts explicit?
\item Does the code depend on an unreviewed size, alignment, promotion, signed overflow or ABI assumption?
\item Could evaluation order, macro expansion, side effects or hidden aliasing change behavior?
\item Is each external symbol defined and declared consistently across translation units?
\item Are thread/resource lifetimes and acquisition/release paths controlled?
\item Are static analyzer errors, open violations and approved deviations traceable and current?
\end{enumerate}

\section{Response playbooks}
\textbf{Unchecked guideline}: record check gap and remediation owner; never infer compliance from missing diagnostics. \textbf{Suspected false positive}: reconstruct the path, checker limitation and independent validation. \textbf{Real Mandatory violation}: fix code or change design/scope before compliance claim. \textbf{Real Required violation}: fix or use formal deviation if allowed. \textbf{Unknown third-party source}: request supplier assurance and assess boundary interfaces.
\section{Build-ready checklist}
\begin{itemize}
\item[$\square$] Compiler success, correct C dialect and warnings review.
\item[$\square$] Tests include invalid inputs, edge values and safe-state behavior.
\item[$\square$] Static analysis version, whole-system boundaries and report are recorded.
\item[$\square$] No unapproved Mandatory or Required violations; policy for Advisory items recorded.
\item[$\square$] Compliance evidence and release scope accepted by designated approver.
\end{itemize}
