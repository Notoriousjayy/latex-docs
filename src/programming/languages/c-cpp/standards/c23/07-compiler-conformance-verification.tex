\chapter*{Sources and interpretation key}
\addcontentsline{toc}{chapter}{Sources and interpretation key}
\textbf{Primary source:} ISO/IEC 9899:2024(en), \emph{Information technology --- Programming languages --- C}, fifth edition (2024). Clause and annex identifiers refer to the supplied licensed standard. This handbook contains original explanations, designs and examples; it does not reproduce the standard. The licensed standard remains the authoritative source for exact wording and conformance decisions.\par
\textbf{Secondary engineering sources:} \url{https://gcc.gnu.org/onlinedocs/gcc/Standards.html}; \url{https://clang.llvm.org/c_status.html}; \url{https://cmake.org/cmake/help/latest/prop_tgt/C_STANDARD.html}. Compiler support and diagnostics are release-specific: verify the installed compiler, target and library before relying on a feature.\par
\begin{keybox}\textbf{Interpretation categories.} \textbf{[STANDARD]} summarizes a requirement, constraint, semantic rule or defined facility and cites the applicable clause. \textbf{[OPTIONAL]} describes conditional or implementation-dependent support. \textbf{[GUIDANCE]} records an engineering recommendation, not an ISO mandate. \textbf{[TEST]} is an original check or exercise; a passing test is evidence but is not proof of full conformity.\end{keybox}

\chapter{Scope: evidence versus certification}
Language conformance has specific ISO meanings. This handbook's tests are evidence toward a scoped claim; they do not constitute an ISO certification, a full compiler conformance suite, or proof that arbitrary programs contain no undefined behavior. A project can impose additional safety constraints while remaining language-conforming. \refcl{4, 5.2.1.3}.
\section{Types of claims}
\begin{itemize}
\item \textbf{Implementation conformance:} claims made by an implementation provider, not inferred from a few examples.
\item \textbf{Program conformance:} determine which assumptions/extensions a program uses and what requirement category applies.
\item \textbf{Engineering policy conformance:} team-specific safeguards (warnings as errors, maximum function length, no risky APIs), explicitly separated from ISO mandates.
\end{itemize}

\chapter{Detailed verification controls}
\subsection{ENV-001: Environment contract}
\textbf{Basis:} \refcl{1, 4, 5.2}.\par\textbf{Verification target:} Hosted/freestanding target, startup behavior, toolchain version and default mode.\par\textbf{Evidence:} Platform factsheet + compile/link probes.\par\guidance\ The audit owner records pass, fail, not applicable or exception, the applicable target and compiler version, and a link to immutable evidence.
\subsection{DIAG-001: Mandatory diagnostics}
\textbf{Basis:} \refcl{5.2.1.3}.\par\textbf{Verification target:} Syntax/constraint negative tests produce at least one diagnostic.\par\textbf{Evidence:} Negative-test records + expected reason.\par\guidance\ The audit owner records pass, fail, not applicable or exception, the applicable target and compiler version, and a link to immutable evidence.
\subsection{TYPE-001: Integer and object representation}
\textbf{Basis:} \refcl{6.2.5--6.2.8}.\par\textbf{Verification target:} Width, alignment, type compatibility and aliases match intended contracts.\par\textbf{Evidence:} Static asserts and target behavior register.\par\guidance\ The audit owner records pass, fail, not applicable or exception, the applicable target and compiler version, and a link to immutable evidence.
\subsection{CONV-001: Conversions and promotions}
\textbf{Basis:} \refcl{6.3}.\par\textbf{Verification target:} Critical conversions are justified and range tested.\par\textbf{Evidence:} Boundary test results + code review.\par\guidance\ The audit owner records pass, fail, not applicable or exception, the applicable target and compiler version, and a link to immutable evidence.

\chapter{Mandatory diagnostics: negative tests}
\section{Compile-time failure fixture}
\begin{lstlisting}
/* Intentionally invalid: two incompatible declarations of one name. */
int duplicate;
double duplicate;
\end{lstlisting}
\standard\ Diagnostic production for constraint/syntax violations is an implementation obligation; error wording is implementation-defined. \refcl{5.2.1.3}.\guidance\ The test should assert nonempty diagnostic output rather than matching one vendor's English message. Some compilers may continue translation.
\section{Positive test and avoidance of a false oracle}
\begin{lstlisting}
#include <limits.h>
#include <stddef.h>
static_assert(CHAR_BIT >= 8);
static_assert(sizeof(char) == 1);
int main(void) { return 0; }
\end{lstlisting}
\guidance\ A \texttt{static\_assert} can verify an environmental assumption, but an application assumption is not automatically a requirement of every implementation.

\section{Register schema}
Capture \texttt{item\_id}, \texttt{standard\_clause}, \texttt{target}, \texttt{compiler\_version}, \texttt{libc\_version}, \texttt{choice}, \texttt{documentation\_uri}, \texttt{reproduction\_test}, \texttt{risk}, \texttt{owner}, and \texttt{date\_verified}. Distinguish implementation-defined choices from unspecified behavior: the latter does not impose an equivalent documentation requirement. \refcl{3.5; Annex J}.
\chapter{Static analysis and dynamic verification}
\section{Recommended tool architecture [GUIDANCE]}
\begin{enumerate}
\item \textbf{Compiler diagnostics:} \texttt{-Wall -Wextra -Wpedantic -Wconversion}, reviewed for portability and vendor differences.
\item \textbf{Static analyzers:} run at least one analyzer that models interprocedural control/data flow on security-sensitive sources.
\item \textbf{Dynamic instrumentation:} AddressSanitizer/UndefinedBehaviorSanitizer and ThreadSanitizer where feasible; report uninstrumented configurations.
\item \textbf{Fuzzing:} parser and decoder entrypoints with seeded regression corpora and crash de-duplication.
\item \textbf{Cross-target:} compare release/debug and multiple data models; require ABI and serialization conformance tests.
\end{enumerate}
\section{What these checks do not prove}
A clean static-analysis report is not completeness evidence. Dynamic sanitizers are incomplete relative to all executions. Build success in C23 mode says little about optional standard attributes, headers, linkable functions or the conditional normative annexes.
\chapter{CI/CD implementation}
\section{CMake: no silent standard downgrade}
\begin{lstlisting}[language=]
cmake_minimum_required(VERSION 3.21)
project(c23_project LANGUAGES C)
add_library(core STATIC src/core.c)
target_include_directories(core PUBLIC include)
set_target_properties(core PROPERTIES
  C_STANDARD 23 C_STANDARD_REQUIRED YES C_EXTENSIONS NO)
include(CTest)
if(BUILD_TESTING)
  add_executable(core_tests tests/core_tests.c)
  target_link_libraries(core_tests PRIVATE core)
  add_test(NAME core_tests COMMAND core_tests)
endif()
\end{lstlisting}
\section{GitHub Actions reference workflow}
\begin{lstlisting}[language=]
name: c23-verification
on:
  push:
  pull_request:
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        compiler: [gcc, clang]
    steps:
      - uses: actions/checkout@v4
      - name: Configure
        run: >-
          cmake -S . -B build
          -DCMAKE_C_COMPILER=${{ matrix.compiler }}
          -DCMAKE_BUILD_TYPE=Debug
      - name: Build
        run: cmake --build build --parallel
      - name: Test
        run: ctest --test-dir build --output-on-failure
\end{lstlisting}
\guidance\ Pin action revisions and hosted runner images under organization policy for stronger reproducibility; support for C23 on the moving runner image must be probed. The example is a starting point, not a supply-chain hardened workflow.
\section{SARIF and findings management}
Use a stable rule ID, severity, file/line, source clause, path explanation, remediation owner, false-positive justification and verification commit. A static analyzer's report of a rule violation is evidence to review, not a conformance determination by itself. Retain baseline hashes and scan configuration.
\chapter{Review gates and exceptions}
\section{Proposed acceptance rule [GUIDANCE]}
\begin{enumerate}
\item No failures in required syntax/constraint diagnostic fixtures.
\item Required tests, compilation and linking pass on every declared target.
\item All high-risk reachable undefined behaviors identified in review and analysis are fixed or explicitly risk accepted with an expiring exception.
\item Every target's implementation-defined behavior register is updated and reviewed.
\item All used optional features and conditional annex claims are backed by probes or vendor documentation.
\item Signed artifact provenance, compiler flags and test results are retained for release review.
\end{enumerate}
