\section{Executive quick reference}
\begin{keybox}
\textbf{Five rules worth memorizing.} (1) The meaning of a standard HTTP field is broadly version-independent; its \emph{wire encoding} is not. (2) Do not carry HTTP/1.1 hop-by-hop fields into HTTP/2 or HTTP/3. (3) In HTTP/2 and HTTP/3, lowercase field names and pseudo-headers are mandatory. (4) Never permit front-end/back-end disagreement about request length, authority, or normalization. (5) A response header is not automatically a security control: the applicable user agent, resource type, redirect chain, origin and cache path determine its effect.
\end{keybox}
\subsection{Normative reading order}
\begin{enumerate}
\item \rf{9110} --- method, status, target URI, fields, conditionals, representation and authentication semantics.
\item \rf{9111} --- cache behavior; \rf{9112} --- HTTP/1.1 message syntax/framing.
\item \rf{9113} and \rf{9114} --- HTTP/2 and HTTP/3 protocol mapping, including pseudo-headers.
\item \rf{7541} (HPACK), \rf{9204} (QPACK), and \rf{9651} (Structured Fields).
\item \stdlink{https://www.iana.org/assignments/http-fields/}{IANA HTTP Field Name Registry} --- authoritative current field names and registry dispositions.
\end{enumerate}

\begin{warnbox}
\textbf{Important distinctions.} ``Registered'' does not guarantee browser implementation, safety, ubiquity, or permission in every protocol version. Likewise, an obsolete field can still appear in legacy traffic. Use \emph{the current specification and endpoint-specific behavior}, not an old taxonomy, to judge compatibility.
\end{warnbox}

\section{Contemporary HTTP field model}
\subsection{Fields, sections and representation metadata}
HTTP fields are name/value pairs in \emph{header} and optionally \emph{trailer} sections. \rf{9110} replaces the outdated ``General / Request / Response / Entity'' classification with semantics defined by each field. A field can describe message content, the selected representation, negotiation preferences, routing, authentication, caching or a response-processing policy. \emph{Message content} is not necessarily the same as \emph{representation data}: a 206 response conveys a partial range, and 304 conveys no content even though it describes a cached representation.

An HTTP field name is case-insensitive semantically. Its name must be serialized in lowercase in HTTP/2 and HTTP/3. A field \emph{line} can appear multiple times, but not every field's grammar permits naive comma-concatenation. \field{Set-Cookie} is a prominent exception; incorrect coalescing can corrupt cookies. Field values must be parsed according to their registered grammar, not with a generic comma split.
\subsection{Three independent encoding planes}
\begin{enumerate}
\item \textbf{Representation/content coding:} \field{Content-Encoding: br} indicates content-coding of representation data. \field{Accept-Encoding} negotiates this property.
\item \textbf{HTTP/1.1 transfer coding and framing:} \field{Transfer-Encoding: chunked} is an HTTP/1.1 message-framing mechanism. It is not a field to forward into HTTP/2 or HTTP/3.
\item \textbf{Field-section compression:} HTTP/2 uses HPACK; HTTP/3 uses QPACK. Neither is controlled by \field{Content-Encoding} and neither is a message body compression scheme.
\end{enumerate}
\subsection{Structured field values}
\rf{9651} (which \emph{obsoletes} \rf{8941}) specifies typed Items, Lists, Dictionaries, parameters and serialized primitives such as integers, strings, dates, booleans and byte sequences. Fields using it include \field{Priority}, \field{Cache-Status}, \field{Signature-Input}, \field{Content-Digest} and \field{Deprecation}. Do not automatically parse legacy headers as Structured Fields: the field's own specification must opt in. For example, \field{Priority: u=0, i} is a Dictionary; \field{Deprecation: @1688169599} is a Structured Date.

\normalsize
\begin{warnbox}
\textbf{Translation invariant:} remove hop-by-hop fields and the names nominated by \field{Connection}; re-derive the authority and message length consistently; do not forward malformed or ambiguous framing. HTTP/2 and HTTP/3 specifically prohibit \field{Connection}, \field{Proxy-Connection}, \field{Keep-Alive}, \field{Transfer-Encoding}, and \field{Upgrade}. Their narrowly defined exception is request \field{TE: trailers}. See \rf{9110} \S7.6.1, \rf{9113} \S8.2.2 and \rf{9114} \S4.2.
\end{warnbox}
\subsection{Pseudo-headers are not ordinary fields}
The request pseudo-header set normally uses \field{:method}, \field{:scheme}, \field{:authority}, \field{:path}; a response uses \field{:status}. They precede normal fields. CONNECT is special: ordinary CONNECT differs in required pseudo-headers, and extended CONNECT has additional rules. Do not try to store a pseudo-header in a general HTTP/1.1 header dictionary or synthesize \field{:status} in an HTTP/1.1 response.

\begin{lstlisting}[caption={HTTP/2 or HTTP/3 logical field sections; not literal wire text}]
:method: GET
:scheme: https
:authority: api.example.test
:path: /v1/items?limit=10
accept: application/json
user-agent: ExampleClient/1.0

:status: 200
content-type: application/json
cache-control: private, max-age=60
\end{lstlisting}
For HTTP/2 these fields are represented in HPACK-compressed HEADERS frames; for HTTP/3 in QPACK-encoded HEADERS frames. The display above is a \emph{conceptual decoding}, not text framing or literal HTTP/1.1 syntax.

\subsection{A practical browser response policy}

Content-Type: text/html; charset=utf-8
X-Content-Type-Options: nosniff
Strict-Transport-Security: max-age=31536000; includeSubDomains
Referrer-Policy: strict-origin-when-cross-origin

\subsection{Conditional GET and cache revalidation}
\begin{lstlisting}
GET /assets/app.css HTTP/1.1
Host: static.example.test
Accept: text/css
Accept-Encoding: br, gzip
If-None-Match: "asset-2026-10-v2"

\end{lstlisting}
\textbf{Interpretation.} The declared byte length is exactly two for the UTF-8 body \texttt{\{\}}. The sample \field{Location} is application-specific; a 202 acknowledgement does not imply that the operation has finished. In logs, authorization credentials must be redacted. \field{Cache-Control: no-store} is a deliberate confidentiality default for this illustrative API.

\subsection{Byte ranges for resumable downloads}
\begin{lstlisting}
GET /download.bin HTTP/1.1
Host: files.example.test
Range: bytes=0-4

HTTP/1.1 206 Partial Content
Content-Type: application/octet-stream
Accept-Ranges: bytes
Content-Range: bytes 0-4/12
Content-Length: 5

HELLO
\end{lstlisting}
\textbf{Interpretation.} The five transferred bytes represent offsets 0 through 4 (inclusive) of a 12-byte selected representation. Validate range bounds; advertise only supported ranges and consider abusive multipart ranges. See \rf{9110} \S14.

\subsection{CORS preflight and credentialed response}
\begin{lstlisting}
OPTIONS /v1/profile HTTP/1.1
Host: api.example.test
Origin: https://app.example.test
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: authorization, content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.test
Access-Control-Allow-Methods: GET, PATCH
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 600
Vary: Origin
\end{lstlisting}
\textbf{Interpretation.} The browser decides whether to allow the cross-origin operation; server-side authorization remains mandatory. For actual credentialed responses, return a specific approved origin, not \texttt{*}, and apply appropriate credential handling. Dynamically reflected allowlisted origins require cache-safe variance. See \stdlink{https://fetch.spec.whatwg.org/}{WHATWG Fetch}.

\subsection{Digest, typed priority and lifecycle signaling}
\begin{lstlisting}
GET /v1/catalog HTTP/1.1
Host: api.example.test
Want-Content-Digest: sha-256=10
Priority: u=2, i

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=300
Deprecation: @1688169599
Link: </v2/catalog>; rel="successor-version"
\end{lstlisting}
\textbf{Interpretation.} \field{Want-Content-Digest} is a preference and does \emph{not} require the server to generate a digest. The response intentionally omits \field{Content-Digest} to demonstrate that point. \field{Priority} is a scheduling hint, not a guarantee. The sample \field{Deprecation} timestamp is historical and demonstrates Structured Date syntax, not a date claim about a real API. The \texttt{successor-version} relation is documented in the link relations registry where applicable; validate any relation type before deployment. See \rf{9530}, \rf{9218}, \rf{9745}.

\subsection{Security-sensitive forwarding across a proxy boundary}
\begin{lstlisting}
# Client -> edge proxy, HTTP/1.1
GET /v1/me HTTP/1.1
Host: public.example.test
Connection: keep-alive
X-Forwarded-Host: attacker.invalid

# Edge -> origin, conceptual HTTP/2 field section
:method: GET
:scheme: https
:authority: service.internal.example
:path: /v1/me
forwarded: for=192.0.2.50;proto=https;host=public.example.test
\end{lstlisting}
\textbf{Interpretation.} The edge removes \field{Connection}, discards any \emph{untrusted} incoming forwarding claims, and constructs a trusted \field{Forwarded} value from verified connection context. Public host routing must use an allowlist. The origin must not trust arbitrary proxies merely because they set a forwarding field. The address \texttt{192.0.2.50} is a documentation-range example.

\section{Operational policies and diagnostic commands}
\subsection{Edge and gateway implementation checklist}
\begin{enumerate}
\item \textbf{Parse:} Enforce one canonical framing interpretation and reject invalid field syntax, forbidden whitespace, control characters and ambiguous duplicates.
\item \textbf{Normalize:} Apply a trusted request-target / authority model and map H1 \field{Host} to H2/H3 \field{:authority} consistently; reject conflicting values.
\item \textbf{Strip:} Remove hop-by-hop options during translation; never forward client-controlled \field{Forwarded} or \field{X-Forwarded-*} values as verified facts.
\item \textbf{Bound:} Limit total header bytes, line count, field value size and trailer size. Reject oversized requests predictably (often 431).
\item \textbf{Protect:} Redact \field{Authorization}, \field{Cookie}, \field{Set-Cookie}, proxy credentials and signing material in telemetry; protect correlation headers from injection.
\item \textbf{Cache:} Determine explicit private/public policy; test authorization, cookies, \field{Vary}, 304 revalidation and CDN overrides.
\item \textbf{Observe:} Log negotiated HTTP version and upstream/downstream versions, normalized authority, request ID and rejection reason without logging credentials.
\item \textbf{Test:} Cover negative cases through every proxy/CDN/load balancer combination, not just against the application process.
\end{enumerate}
\subsection{Read-only inspection with curl}
\begin{lstlisting}
# Read response headers through each supported HTTP version.
curl --http1.1 -sS -D - -o /dev/null https://example.test/
curl --http2   -sS -D - -o /dev/null https://example.test/
curl --http3   -sS -D - -o /dev/null https://example.test/

# Include negotiated protocol information in output.
curl -sS -o /dev/null -w 'HTTP %{http_version}\n' https://example.test/

# Conditional request; review status and validators.
curl -i -H 'If-None-Match: "asset-2026-10-v2"' \
  https://example.test/assets/app.css

# Inspect certificates / negotiated ALPN where TLS is used.
openssl s_client -connect example.test:443 -servername example.test \
  -alpn 'h2,http/1.1' </dev/null
\end{lstlisting}
\textbf{Environment caveats.} \texttt{curl --http3} requires a libcurl build with HTTP/3 support and an HTTP/3-capable server/path. \texttt{-D -} prints response headers; use \texttt{-v} cautiously because it may expose credentials. \texttt{-I} sends HEAD, which is useful but not identical to testing GET behavior. Avoid using production auth tokens in shell history or logged examples.
