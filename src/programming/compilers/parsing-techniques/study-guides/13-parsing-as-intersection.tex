\section{Chapter orientation}
This guide follows Chapter 13 of Grune and Jacobs, \emph{Parsing Techniques: A Practical Guide}, second edition. Printed pages 425--442. The focus is on reconstructing the chapter's reasoning, verifying explicit assumptions, and translating its central idea into a controlled engineering experiment. This is an independently authored learning guide, not a substitute for the book.

\section{Learning objectives}
\begin{enumerate}
\item Define and differentiate intersection construction using a small grammar and its accepted language.
\item Define and differentiate finite-state input descriptions using a small grammar and its accepted language.
\item Construct an example or counterexample illustrating unknown tokens and filtering.
\item Evaluate the operational constraints of earley-style optimization on automata and retain reproducible evidence.
\end{enumerate}

\section{Technical deep dive: finite-state input constraints}
An input automaton can describe a set of possible token sequences rather than one fixed string. Intersecting its paths with a context-free grammar filters the uncertainty to syntactically admissible sequences. A product construction tracks grammatical variables alongside automaton start/end states. Its space usage depends on the number of automaton states and grammar rules; record pruning and avoid assuming that a compact input automaton guarantees a compact intersection representation.
\section{Worked reasoning prompt}
Represent token uncertainty with a small finite automaton rather than one fixed word. Derive each intermediate state by hand; write the invariant that justifies advancing to the next state. Identify the accepted result and one structurally similar rejected result.
\section{Implementation and laboratory assignment}
Build a product-style recognition exercise and record intermediate grammar size. Record the grammar, input corpus, expected outputs, maximum input size and a regression test for the principal failure mode. For each test, independently justify the expected result rather than reading it from the program.
\section{Failure analysis and technical discussion}
Finite-state intersection can blow up in intermediate states; record representation and pruning. Explain how your implementation would detect the failure and which diagnostics can distinguish grammar invalidity from resource exhaustion.
\section{Evidence checklist}
\begin{itemize}
\item Grammar and accepted-language specification with version and fixtures.
\item Hand-executed trace and implementation trace for the same accepted and rejected cases.
\item At least one adversarial or boundary input and an explanation of the expected behavior.
\item Correctness argument, complexity claim with assumptions, and unit-test output.
\item Cross-reference to a related chapter and one explicit unresolved question.
\end{itemize}
\section{Independent examination}
\begin{enumerate}
\item Explain the algorithm without using implementation-language details.
\item Give a proof sketch or invariant for acceptance and termination on the specified grammar class.
\item Change one grammar rule and predict which tests must change before running them.
\item Compare behavior on malformed input, ambiguous input, and input beyond configured resource limits.
\end{enumerate}
