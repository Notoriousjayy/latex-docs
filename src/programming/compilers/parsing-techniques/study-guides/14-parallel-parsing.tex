\section{Chapter orientation}
This guide follows Chapter 14 of Grune and Jacobs, \emph{Parsing Techniques: A Practical Guide}, second edition. Printed pages 443--472. The focus is on reconstructing the chapter's reasoning, verifying explicit assumptions, and translating its central idea into a controlled engineering experiment. This is an independently authored learning guide, not a substitute for the book.

\section{Learning objectives}
\begin{enumerate}
\item Define and differentiate motivations and overhead using a small grammar and its accepted language.
\item Define and differentiate concurrent parsers using a small grammar and its accepted language.
\item Construct an example or counterexample illustrating process configurations.
\item Evaluate the operational constraints of circuit-style cyk and asymptotic depth and retain reproducible evidence.
\end{enumerate}

\section{Technical deep dive: work versus span}
In CYK, a chart cell of span length $\ell$ depends only on shorter spans. Cells of equal length may be scheduled concurrently once shorter spans finish. Sequential work remains the sum over all cells and splits, whereas critical-path depth depends on processing strategy and parallel primitive costs. Report $W$ (total work), $D$ (critical-path span), processor count $P$, communication cost and allocation overhead; theoretical parallelism $W/D$ is only an upper bound on useful speedup.
\section{Worked reasoning prompt}
Identify independent CYK subproblems at equal span length. Derive each intermediate state by hand; write the invariant that justifies advancing to the next state. Identify the accepted result and one structurally similar rejected result.
\section{Implementation and laboratory assignment}
Design a parallel schedule and quantify work, depth, communication, and memory bandwidth. Record the grammar, input corpus, expected outputs, maximum input size and a regression test for the principal failure mode. For each test, independently justify the expected result rather than reading it from the program.
\section{Failure analysis and technical discussion}
Parallel speedup is not guaranteed by theoretical depth alone. Explain how your implementation would detect the failure and which diagnostics can distinguish grammar invalidity from resource exhaustion.
\section{Evidence checklist}
\begin{itemize}
\item Grammar and accepted-language specification with version and fixtures.
\item Hand-executed trace and implementation trace for the same accepted and rejected cases.
\item At least one adversarial or boundary input and an explanation of the expected behavior.
\item Correctness argument, complexity claim with assumptions, and unit-test output.
\item Cross-reference to a related chapter and one explicit unresolved question.
\end{itemize}
\section{Independent examination}
\begin{enumerate}
\item Explain the algorithm without using implementation-language details.
\item Give a proof sketch or invariant for acceptance and termination on the specified grammar class.
\item Change one grammar rule and predict which tests must change before running them.
\item Compare behavior on malformed input, ambiguous input, and input beyond configured resource limits.
\end{enumerate}
