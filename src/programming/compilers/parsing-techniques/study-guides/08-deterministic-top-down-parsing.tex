\section{Chapter orientation}
This guide follows Chapter 8 of Grune and Jacobs, \emph{Parsing Techniques: A Practical Guide}, second edition. Printed pages 235--262. The focus is on reconstructing the chapter's reasoning, verifying explicit assumptions, and translating its central idea into a controlled engineering experiment. This is an independently authored learning guide, not a substitute for the book.

\section{Learning objectives}
\begin{enumerate}
\item Define and differentiate predictive tables using a small grammar and its accepted language.
\item Define and differentiate first and follow sets using a small grammar and its accepted language.
\item Construct an example or counterexample illustrating ll(1) conflicts.
\item Evaluate the operational constraints of ll(k) and extended ll and retain reproducible evidence.
\end{enumerate}

\section{Technical deep dive: predictive table construction}
For production $A\to\alpha$, add it to $M[A,a]$ for every terminal $a\in \mathrm{FIRST}(\alpha)\setminus\{\epsilon\}$. When $\epsilon\in\mathrm{FIRST}(\alpha)$, also place it in cells for $b\in\mathrm{FOLLOW}(A)$. More than one distinct production in one cell is an LL(1) conflict. The deterministic recognizer expands stack nonterminals using the lookahead cell and consumes a terminal only when it matches the current input symbol. Test end-marker handling explicitly.
\section{Worked reasoning prompt}
Calculate FIRST/FOLLOW for $S\to aA$, $A\to bA\mid\epsilon$. Derive each intermediate state by hand; write the invariant that justifies advancing to the next state. Identify the accepted result and one structurally similar rejected result.
\section{Implementation and laboratory assignment}
Construct an LL(1) table with conflict detection and demonstrate a successful table trace. Record the grammar, input corpus, expected outputs, maximum input size and a regression test for the principal failure mode. For each test, independently justify the expected result rather than reading it from the program.
\section{Failure analysis and technical discussion}
A table conflict means the grammar is not LL(1); it does not mean its language is inherently ambiguous. Explain how your implementation would detect the failure and which diagnostics can distinguish grammar invalidity from resource exhaustion.
\section{Evidence checklist}
\begin{itemize}
\item Grammar and accepted-language specification with version and fixtures.
\item Hand-executed trace and implementation trace for the same accepted and rejected cases.
\item At least one adversarial or boundary input and an explanation of the expected behavior.
\item Correctness argument, complexity claim with assumptions, and unit-test output.
\item Cross-reference to a related chapter and one explicit unresolved question.
\end{itemize}
\section{Independent examination}
\begin{enumerate}
\item Explain the algorithm without using implementation-language details.
\item Give a proof sketch or invariant for acceptance and termination on the specified grammar class.
\item Change one grammar rule and predict which tests must change before running them.
\item Compare behavior on malformed input, ambiguous input, and input beyond configured resource limits.
\end{enumerate}
