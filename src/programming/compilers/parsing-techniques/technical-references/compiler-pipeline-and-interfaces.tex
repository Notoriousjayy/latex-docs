\section{Reference compiler pipeline}
Source bytes $\to$ decode $\to$ tokens $\to$ syntax tree $\to$ AST $\to$ name resolution/type rules $\to$ intermediate representation $\to$ optimization $\to$ emission. Each stage has an explicit data contract and must preserve source span provenance through transformations where diagnostics are possible. Compilation should not execute untrusted source while attempting to validate its syntax.
\section{Token contract}
A token carries kind, original lexeme or canonical value, start/end source offset, and line/column presentation mapping. Declare byte versus Unicode scalar indexing; mixing units breaks diagnostics and potentially security policy. A lexer must surface invalid encoding, unterminated strings, oversized literals and comments without unbounded buffering.
\section{AST and ownership}
Define distinct AST node types and ownership. Python immutable dataclasses or C++ variant/value objects suit teaching projects; production designs depend on lifetime, incremental updates, serialization, and source maps. AST invariants include ordered child spans, operator precedence encoded in structure, and no unvalidated pointer ownership.
\section{Semantic pipeline}
Create lexical scope tables, bind symbols to declarations, validate types, and report source-located violations. For a small calculator, distinguish syntax $1+2$ from a semantic rule such as division by zero. Never suppress lexical/syntactic errors as semantic successes.
\section{Safe evaluation boundary}
Treat the parser as a validator and AST producer, not an authorization decision. If a laboratory evaluates arithmetic, only execute a deliberately restricted expression AST and bound total nodes and numeric magnitude. No reflection, filesystem, network, import, or shell execution.
\section{API and testing contract}
Define $\mathtt{parse(source,limits)}\to\mathtt{Result(AST,diagnostics)}$. Guarantee deterministic error codes, controlled maximum work, clear stop semantics, and stable test fixtures. Test every stage independently, then end-to-end using both success and rejection cases.\PTSource{Chapters 16--17; pipeline architecture is an engineering extension.}
