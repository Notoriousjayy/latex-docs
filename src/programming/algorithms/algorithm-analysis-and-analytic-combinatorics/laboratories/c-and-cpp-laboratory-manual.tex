\section{Compiler and portability baseline}
C++17 and a standards-conforming compiler; C11 for the separate occupancy exercise. Use release optimization \texttt{-O2} for elapsed-time reports, and a separate debug compilation with warnings for correctness checks. Capture compiler version and flags. Do not treat undefined behavior or overflow as evidence for an algorithmic claim.
\section{LAB-CPP01: mergesort recurrence and cost instrumentation}
Implement a stable two-way mergesort counting only element-to-element comparisons. For a conventional merge without sentinels, the exact comparison count depends on the values, bounded by the merge length minus one when both runs are nonempty. Therefore $n\log_2n$ is a useful scale, not an exact per-input count for this implementation. Compare sorted, reversed and random permutations at powers of two and nearby sizes; derive an appropriate recurrence for a \emph{worst-case upper bound}. Keep copying/moves separate if instrumented.
\section{LAB-CPP02: inversions, insertion sort and hashing}
\textbf{Part A.} Confirm for every permutation with $n\le7$ that the input inversion count equals the number of shifts by the supplied insertion-sort implementation. Compare the uniform-permutation mean to $n(n-1)/4$.\par
\textbf{Part B.} Assign $m$ independent random integers to $b$ buckets with reproducible seeds, count bucket occupancies and colliding pairs (all keys in the same bucket, not just duplicate keys). Report expected $m/b$ load and $\binom m2/b$ colliding pairs across repeated trials. For open addressing, do not reuse chain-length results as probe-count results.
\section{LAB-C01: C11 bucket occupancy}
Compile the provided C11 reference with warnings and check that total recorded bucket load equals $m$ and collision count equals the sum of $x_j(x_j-1)/2$ across buckets. Compare at $b=4,16,64$ and discuss sampling limitations of the simple pseudorandom generator and hash model used. This is a didactic simulation, not a cryptographically secure implementation.
\section{Commands}
\begin{enumerate}
\item Compile with \texttt{cmake -S . -B build -DCMAKE\_BUILD\_TYPE=Release} then \texttt{cmake --build build} from \texttt{laboratories/code}.
\item Run \texttt{./build/analysis\_cpp merge 128 71} and \texttt{./build/analysis\_cpp insert 128 71}.
\item Run the C++ occupancy example with \texttt{./build/analysis\_cpp occupancy 512 71 64}. Then run the C11 example separately: \texttt{./build/occupancy\_c 512 64 71}.
\item Run \texttt{ctest --test-dir build --output-on-failure}; preserve failure output and compiler version.
\end{enumerate}
\section{Assessment gate}
A passing submission has test results, exact operation units, no omitted failure cases, at least three independent sizes, an input-model qualification, and a concise comparison of mathematical growth to empirical timing. Use the proof-assessment and laboratory-report forms.
