\section{Objective and measurement hierarchy}
A benchmark cannot prove an asymptotic theorem. It can validate finite-size predictions, detect broken implementations, and estimate machine-dependent effects. Measure in layers: (1) exact operation counts, (2) monotonic-clock elapsed time, (3) optional hardware counters with documented tools. Prioritize operation-count correctness before throughput.
\section{Experiment design protocol}
\begin{enumerate}
\item \textbf{Hypothesis.} Write a falsifiable expression such as $C(n)=an\log_2 n+bn+o(n)$ and identify whether $a,b$ are derived or fitted.
\item \textbf{Input populations.} Include random permutations, sorted, reversed, nearly sorted, repeated keys, and a realistic domain trace only if lawfully available.
\item \textbf{Factorization.} Vary one parameter at a time or use a declared factorial design; hold data generation outside timed regions.
\item \textbf{Warmup and replication.} Establish a warmup policy; collect at least 15 independent repetitions for each configuration when feasible. Set fixed, recorded seeds and shuffle case order.
\item \textbf{Environment.} Record processor, cores, memory, OS, compiler/interpreter version, optimization, CPU governor when known, and commit hashes.
\item \textbf{Analysis.} Report median and quantiles; include raw samples and uncertainty. Compare model-predicted operation counts to observed counts without mixing units.
\item \textbf{Reproduction.} Supply commands, datasets or deterministic seeds, program hashes, and a machine-readable results schema.
\end{enumerate}
\section{Recommended quantities}
For each row record $\{\mathrm{algorithm},\mathrm{language},\mathrm{model},n,\mathrm{seed},\mathrm{repeat},\mathrm{ops},\mathrm{elapsed\_ns},\mathrm{correct}\}$. Use CSV with a header and no unit ambiguity. For latency $t_i$, the median is robust to occasional pauses, but does not replace all raw observations. A bootstrap interval may summarize uncertainty, provided sampling units and resampling method are explicit.
\section{Scaling analyses}
Given times $t(n)$ and $t(2n)$, estimate the doubling ratio $R(n)=t(2n)/t(n)$; compare to $2$ for linear work, roughly $2(1+1/\log_2 n)$ for $n\log n$ work, and $4$ for quadratic work. Interpret ratios only once startup and memory-regime effects are accounted for. For candidate model $f(n)$, plot $t(n)/f(n)$ and $C(n)/f(n)$ separately; stable operation normalization is stronger evidence about algorithmic structure than stable timing normalization.
\section{Fair Python versus C++ comparisons}
Cross-language absolute elapsed times incorporate runtime and compiler differences; do not use them to infer algorithmic efficiency in isolation. Require identical input files, comparable algorithm variants, consistent key types and semantics, independent validation of counts, and explicit interpreter/compiler versions. Report both absolute times and normalized operation counts.
\section{Common threats to validity}
\begin{longtable}{p{0.21\linewidth}p{0.65\linewidth}}\toprule Threat & Mitigation \\ \midrule
Timing resolution & Increase work per sample and report clock API \\
Thermal/frequency changes & Randomize order and capture machine state when available \\
Allocation or GC & Record configuration; separate allocation costs from comparisons \\
Cache effects & Test multiple memory footprints and identify transition regions \\
Input bias & Distinguish uniform permutations from empirical distributions \\
Instrument overhead & Run instrumented and uninstrumented variants; compare costs separately \\
Discarded failures & Keep failed samples with error state; never silently drop them \\
\bottomrule\end{longtable}
\section{Publication gates}
\begin{itemize}\item Correctness and cost-counter invariants pass. \item Raw results and program versions archived. \item Hypothesis, estimator, uncertainty and exclusions documented. \item At least one alternate input distribution tested. \item Results replicated on a fresh process; independent machine optional but desirable.\end{itemize}
