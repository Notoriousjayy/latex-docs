\begin{CornellOverviewBox}{Review Orientation}
\textbf{Central problem.} Audit variables, control flow, functions, and memory management as composable building blocks whose local mistakes can create system-level vulnerabilities.
\textbf{Why it matters.} Security reviewers use this material to connect attacker-controlled conditions to violated invariants, consequential operations, and defensible remediation.
\textbf{Prerequisites.} C language semantics, data structures, control flow, functions, and dynamic allocation.
\textbf{Assessment relationship.} It converts language hazards into repeatable code-review strategies for common program constructs.
\end{CornellOverviewBox}
\section{Learning Objectives}
\begin{itemize}
\item Explain the security significance of variable relationships.
\item Identify attacker influence and failed assumptions associated with structures and objects.
\item Trace security-relevant data or state through initialization.
\item Evaluate whether controls addressing arithmetic boundaries and type confusion preserve the intended invariant.
\item Audit implementation and error paths related to lists and tables.
\item Distinguish safe and unsafe uses of looping constructs.
\item Diagnose a failure involving flow transfers from concrete evidence.
\item Verify remediation and test coverage for switch statements.
\end{itemize}

\term{Looping constructs}\\[-0.1em]{\small What proves that a loop stays in bounds and terminates?} & Review initialization, condition, update, integer range, mutation inside the body, and exceptional exits. \term{Allocation logs and scorecards}\\[-0.1em]{\small How can allocators be reviewed consistently?} & Catalog wrappers and allocators, their zero-size behavior, overflow handling, initialization, failure convention, and matching release function. Wrappers can add safety or conceal assumptions.\par\smallskip\textbf{Audit move:} Build an allocator scorecard and map every allocation family to its deallocator. \\\hline
\term{Allocation functions}\\[-0.1em]{\small Which inputs determine allocation safety?} & The reviewer must verify count and size arithmetic, alignment, maximums, zero-size behavior, failure handling, and whether the returned memory is initialized before use.\par\smallskip\textbf{Audit move:} Audit arithmetic before the call and all paths after a null or exceptional result. \\\hline
\term{Error domains}\\[-0.1em]{\small Can allocation failure corrupt higher-level state?} & Partial construction may leave ownership split across layers, producing leaks, double releases, stale references, or use of incomplete objects. Recovery must restore a clearly defined state.\par\smallskip\textbf{Audit move:} Force failure at each acquisition point and verify rollback invariants. \\\hline
\term{Double-free and lifetime errors}\\[-0.1em]{\small What happens when ownership is ambiguous?} & Multiple aliases or inconsistent cleanup can release an object twice or use it after release. Allocator reuse can turn stale access into corruption of a new object.\par\smallskip\textbf{Audit move:} Track unique ownership, reference transitions, cleanup labels, and alias invalidation. \\\hline
\end{longtable}
\begin{CornellSummaryBox}{Section Summary}
Allocation review follows size calculation, ownership, lifetime, and error domains from acquisition through final release.
\end{CornellSummaryBox}
\begin{CornellLegacyBox}{Historical Context}
Named allocator behaviors and debugging conventions vary by platform; verify actual wrapper semantics and runtime behavior for the reviewed build.
\end{CornellLegacyBox}

\section{Chapter Synthesis}
Program constructs become vulnerabilities when their implicit contracts are inconsistent across paths or components. Reviewers should make relationships, ranges, ownership, side effects, and required postconditions explicit, then test them at boundaries and failures. Memory lifetime and values controlling allocation or indexing deserve priority because small inconsistencies can become corruption or control-flow errors.
\section{Self-Test Questions}
\begin{enumerate}
\item Which values must remain consistent?
\item How does object mismanagement create vulnerabilities?
\item Can a value be read before it has a valid meaning?
\item How can metadata become internally contradictory?
\item Which indexing and linkage invariants protect containers?
\item What proves that a loop stays in bounds and terminates?
\item \textbf{Scenario:} A function returns a negative error code, but its caller stores the result in an unsigned variable used as a copy length. What failure pattern is present?
\item \textbf{Scenario:} An error path frees an object and jumps to shared cleanup, which frees it again. How should the fix be evaluated?
\end{enumerate}

\subsection*{Answer Key}
\begin{enumerate}
\item Lengths, pointers, capacities, counts, states, and ownership flags often describe one logical object. Updating one without the others creates stale metadata and unsafe reads, writes, or authorization decisions.
\item Incorrect casts, partial initialization, stale pointers, layout assumptions, and confused ownership can cause one object to be interpreted as another or used outside its lifetime.
\item Uninitialized storage can influence branches, lengths, pointers, or output. Partial error paths and structure padding may also disclose stale data even when normal initialization appears complete.
\item Overflow, truncation, and incorrect type interpretation can turn validated values into unsafe sizes or dispatch choices. Type confusion is especially dangerous when layouts overlap enough to pass superficial checks.
\item Container safety depends on valid counts, sentinel handling, link consistency, capacity, sorting assumptions, and ownership. Corruption can lead to out-of-bounds access, cycles, or use-after-free.
\item Review initialization, condition, update, integer range, mutation inside the body, and exceptional exits. Attacker-controlled counts or stalled progress can cause memory errors or denial of service.
\item The caller misinterprets the return-value contract, converting an error sentinel into a large length. Review signedness, error handling, and every sibling call site.
\item Clarify ownership and cleanup postconditions, ensure each resource has one release responsibility, invalidate aliases after transfer or release, and test failure at every acquisition step.
\end{enumerate}
