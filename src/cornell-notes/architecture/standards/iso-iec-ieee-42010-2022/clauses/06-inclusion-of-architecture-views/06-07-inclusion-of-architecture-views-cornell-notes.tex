\begin{CornellOverviewBox}{Overview}
{\Large\bfseries\textcolor{CNavy}{Section 6.7: Inclusion of architecture views}}\\[3pt]
{\small\textbf{Classification:} Normative}\\
{\small\textbf{Learning objective:} Identify the mandatory, recommended, and permitted provisions governing inclusion of architecture views.}
\end{CornellOverviewBox}
\vspace{3pt}

\begin{CornellNotesTable}
\CornellNoteRow{Purpose}{Establishes how architecture views are included, governed, versioned, and used to address perspectives, concerns, and aspects.}
\CornellNoteRow{Requirement}{\begin{itemize}[leftmargin=*,nosep,topsep=1pt]
\item A conforming architecture description must include one or more architecture views for each architecture viewpoint used.
\item Each architecture view must include version identification as specified by the organization and/or project.
\item Each stakeholder perspective identified by the AD in accordance with 6.3 must be addressed by at least one view in accordance with the view’s governing viewpoint.
\item Each concern identified by the AD in accordance with 6.4 must be addressed by at least one view in accordance with the view's governing viewpoint.
\item Each architecture aspect identified by the AD in accordance with 6.5 must be addressed by at least one view in accordance with the view’s governing viewpoint.
\item Each architecture view must adhere to the conventions of its governing architecture viewpoint.
\item Each architecture view must include or provide a reference for:
\item Required content: identifying and supplementary information as specified by the organization and/or project
\item Required content: identification of its governing architecture viewpoint
\item Required content: one or more view components that address all of the concerns (per 6.4) framed by its governing architecture viewpoint (per 6.6) and that cover some or all of the entity of interest with respect to that viewpoint; and
\item Required content: the recording of any known issues within a view with respect to its governing architecture viewpoint
\end{itemize}}
\CornellNoteRow{Permission}{\begin{itemize}[leftmargin=*,nosep,topsep=1pt]
\item Each architecture view may address more than one concern.
\item An architecture description may include other information which is not part of any architecture view.
\end{itemize}}
\CornellNoteRow{Example / application}{Several kinds of views can be described for a functional viewpoint: for example, functional chains express the behaviour and function trees express decomposition.}
\CornellNoteRow{Interpretive note}{\begin{itemize}[leftmargin=*,nosep,topsep=1pt]
\item When a viewpoint governs more than one view in a particular AD, they are describing one architecture.
\item “Known issues” per d) include unresolved issues, risks, exceptions and deviations from the governing model kinds or legends. Open issues can lead to decisions to be made. Exceptions and deviations can be documented as decision outcomes and rationale (per 6.10).
\end{itemize}}
\CornellNoteRow{Related sections}{6.3, 6.4, 6.5, 6.6, 6.10}
\CornellNoteRow{Conformance check}{\begin{itemize}[leftmargin=*,nosep,topsep=1pt]
\item A conforming architecture description must include one or more architecture views for each architecture viewpoint used
\item Each architecture view must include version identification as specified by the organization and/or project
\end{itemize}}
\CornellNoteRow{Active recall}{\begin{itemize}[leftmargin=*,nosep,topsep=1pt]
\item Which provisions in Inclusion of architecture views are mandatory for conformance?
\item Which provisions are recommendations or permissions rather than requirements?
\end{itemize}}
\end{CornellNotesTable}


\begin{CornellSummaryBox}{Summary}
Establishes how architecture views are included, governed, versioned, and used to address perspectives, concerns, and aspects. For conformance, its mandatory provisions must be satisfied, including: A conforming architecture description must include one or more architecture views for each architecture viewpoint used; Each architecture view must include version identification as specified by the organization and/or project. The section also explicitly permits: Each architecture view may address more than one concern.
\end{CornellSummaryBox}
