\begin{CornellNotesTable}
\CornellNoteRow{Purpose / key concept}{An ADF establishes a common practice for creating, interpreting, analysing and using ADs within a particular domain of interest, e.g. defense, aerospace and banking.}
\CornellNoteRow{Core details}{\begin{itemize}[leftmargin=*,nosep,topsep=1pt]
\item An ADF can also guide or serve as a reference for one or more than one specialized ADF.
\item For a generalized entity of interest within the context of a particular domain of practice, an ADF intended as a reference typically identifies architecture viewpoints for expected or known architecture considerations, often as stakeholder perspectives, concerns or aspects related to structure, function (both behaviour and fitness) and life cycle.
\end{itemize}}
\CornellNoteRow{Distinction}{An ADF organizes reusable conventions and practices for a domain or community; an ADL supplies syntax and semantics for expressing architectural information.}
\CornellNoteRow{Study relationship / visual insight}{Study relationship: an ADF applies to a domain, identifies typical stakeholders and concerns, specifies viewpoints and a structuring formalism, defines structural categories, and can contain correspondence methods.}
\CornellNoteRow{Example / application}{Well known structuring formalisms include: GERAM cube in ISO 15704, Reference Architectural Model Industrie 4.0 (RAMI 4.0), TOGAF phases (Business, Data, Application and Technology), NAF grid, UAF grid, and Zachman Framework matrix.}
\CornellNoteRow{Interpretive note}{\begin{itemize}[leftmargin=*,nosep,topsep=1pt]
\item Particular architecture decisions are made in ADFs: selection of stakeholders and related concerns, specific aspects and stakeholder perspectives. An ADF will structure ADs according to these decisions.
\end{itemize}}

\begin{CornellSummaryBox}{Summary}
An architecture description framework establishes reusable practice for creating, interpreting, analysing, and using architecture descriptions within a domain or community. It identifies typical concerns and viewpoints and can organize them through structuring formalisms and structural categories. Unlike an architecture description language, a framework organizes broader conventions and practices rather than merely supplying syntax and semantics.
\end{CornellSummaryBox}
