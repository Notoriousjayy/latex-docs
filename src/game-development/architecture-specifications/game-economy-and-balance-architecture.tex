\section{Purpose and provenance}
Separate balance parameter models from runtime rules while protecting conserved resources and controlled experiment evidence.

Book-aligned conceptual chapters: 12, 13, 32. The architecture, contracts, constraints, and diagrams are original engineering proposals, not architectures claimed to be supplied by Schell.


\section{Stakeholder concerns and boundaries}
\begin{itemize}
\item Player: understandable, responsive, accessible experience.
\item Game designer: explicit rule changes and observable consequences.
\item Gameplay engineer: state ownership, testability, maintainability, debugging.
\item QA/research: reliable test evidence and reproducible findings.
\item Security/privacy owner: minimal data collection, abusive-input boundaries, safe operations.
\end{itemize}

\section{Architecture decisions}
\begin{enumerate}
\item Parameter sets are versioned data and validated against type, range, and cross-field constraints.
\item Sources and sinks are named and logged independently; grants are idempotent when backed by a server.
\item Analytical model and Monte Carlo models share defined semantics but need not share PRNG implementations.
\item Player feedback is reviewed with simulation evidence; neither replaces the other.
\item Release gates require stratified balance evidence and an exploit review.
\end{enumerate}

\section{Quality attributes and verification}
\begin{itemize}
\item Each grant and spend is atomic in its authority domain.
\item No legal sequence makes a bounded wallet negative.
\item Simulation runs record count, seed, parameter revision, and sampling assumptions.
\item Balance claims include variability rather than only a single mean.
\end{itemize}

\section{Threats, trade-offs, and alternatives}
\begin{enumerate}
\item For each exposed input and state owner, list abuse cases and assign prevention, detection, and recovery controls.
\item Compare two alternative decompositions using latency, coupling, observability, and test isolation.
\item Record who signs off on portability, security, privacy, and player-facing changes.
\item Do not infer that software correctness demonstrates an engaging player experience.
\end{enumerate}
