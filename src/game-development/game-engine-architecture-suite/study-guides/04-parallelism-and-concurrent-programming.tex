\section{Reading crosswalk and prerequisites}
Book chapter 4; Part Foundations; sections 4.1--4.11. Read the source chapter first, then perform the independent engineering activities below. Distinguish statements from the book from proposed implementations and experiments.

Required prior evidence: selected exercises from chapters 2 and 3, or a documented equivalent baseline.

\section{Observable learning outcomes}
\begin{itemize}
\item Explain and defend data-race freedom in terms of contracts, ownership and measurable behavior.
\item Explain and defend mutex and atomics in terms of contracts, ownership and measurable behavior.
\item Explain and defend job dependencies in terms of contracts, ownership and measurable behavior.
\item Explain and defend SIMD and GPU execution in terms of contracts, ownership and measurable behavior.
\end{itemize}
\section{Engineering interpretation}
A correct worker pool needs explicit ownership, synchronization, ordering and stop behavior; lock-free is not automatically low-latency or safe.

\section{Guided reading and reasoning}
\begin{enumerate}
\item Differentiate concurrency, parallel execution and asynchronous tasks.
\item Draw a happens-before graph for dependent jobs and distinguish mutex safety from progress guarantees.
\item Compare a parallel update partition against its sequential baseline and justify cancellation/shutdown.
\end{enumerate}
\section{Implementation exercise}
Implement a bounded worker experiment with completion counting and safe teardown; inspect race-detector results when available.

\subsection{Minimum engineering specification}
\begin{itemize}
\item State all preconditions, postconditions and owned resources in a short interface contract.
\item Make a deterministic test case and a negative/error-path test case.
\item Record CPU, platform, compiler or Python version, operating system, seed, and relevant runtime settings.
\item Keep the exercise separate from proprietary game code or assets; produce original diagrams and sample data.
\end{itemize}
\section{Validation and adversarial cases}
Verify that every input item is processed once and results match sequential output over repeated runs.

\begin{itemize}
\item What invariant could fail while a demo still appears correct?
\item What input or platform assumption invalidates your design?
\item How would you diagnose a regression from logs, measurements and a minimal reproduction?
\end{itemize}
\section{Study questions}
\begin{enumerate}
\item What is the principal abstraction boundary introduced in this chapter?
\item Which performance/correctness trade-off does that boundary enable?
\item How does this subsystem coordinate with resource lifetime, simulation time and threading?
\item What would be a counterexample to your assumed invariant?
\end{enumerate}
\section{Exit criteria and artifacts}
\begin{itemize}
\item One-page technical decision note with alternatives and constraints.
\item Runnable source or a precise pseudocode specification; include test commands.
\item Test transcript, benchmark/data capture where applicable, and a written conclusion.
\item Self-assessment: identify one unresolved hazard and how you would validate it.
\end{itemize}
