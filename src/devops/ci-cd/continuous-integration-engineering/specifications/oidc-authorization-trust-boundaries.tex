\section{Status and scope}
Proposed reference architecture. No production cloud environment or organizational authorization is implied. Illustrative diagrams reside in this suite and should be verified against the actual runner, GitHub and cloud trust configuration.

\section{Assets}
Deployment role, infrastructure state, target account, artifact registry, approval logs and workflow definition. Compromise of a workflow or runner must not grant broader authorization than explicitly intended.

\section{Federation}
GitHub issues a short-lived signed identity token to a job with id-token: write. Cloud STS validates token claims; audience, subject, repository and expected workflow/environment claims must match the actual provider configuration. Subject patterns can change, so test claims rather than inventing a string.

\section{Safety controls}
Separate staging and production roles and accounts; avoid long-lived cloud keys; use permissions boundaries and small action scope; allow identity lookup before any mutating command; do not allow PR-controlled input to choose role ARN.

\section{Denial tests}
Untrusted branch, wrong repository, wrong audience, unapproved environment and unintended reusable workflow must each fail assumption or authorization. Capture denial without leaking token or payload.

\section{Accountability}
Reviewers approve role/policy changes independently from application PRs. Rotate/disable federation on compromise and preserve cloud audit events tied to workflow run id.

\section{Acceptance review}
\begin{itemize}
\item Record context, container/module responsibilities and owning teams.
\item Identify untrusted inputs and every elevation or data transfer.
\item Exercise one successful path and at least one deliberate unauthorized path.
\item Identify release restoration point and hard-stop thresholds.
\item Attach reviewer sign-off and an architecture decision record for nontrivial trade-offs.
\end{itemize}
