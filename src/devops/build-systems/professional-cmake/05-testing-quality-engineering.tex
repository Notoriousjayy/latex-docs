\textbf{Rule:} CTest schedules an executable and interprets its result;
it does not create assertions in your production code. A successful test
run proves only that the exercised assertions passed under the selected
environment.

\chapter{Registering deterministic
tests}\label{registering-deterministic-tests}

\begin{lstlisting}
include(CTest)
if(BUILD_TESTING)
  add_executable(core_tests tests/math_tests.cpp)
  target_link_libraries(core_tests PRIVATE BuildSuite::core)
  add_test(NAME core.math COMMAND core_tests)
  set_tests_properties(core.math PROPERTIES
    TIMEOUT 15
    LABELS "unit;core;smoke"
  )
endif()
\end{lstlisting}

\begin{lstlisting}[language=sh]
cmake --preset ci-debug
cmake --build --preset ci-debug
ctest --preset ci-debug --output-on-failure
ctest --test-dir build/ci-debug -L smoke --output-junit build/junit.xml
\end{lstlisting}

Record the CMake, CTest, compiler and test binary versions, selected
preset and git revision. Do not make a test depend on its execution
order unless that ordering is an explicit fixture relationship. Tests
with shared directories, ports or services need resource isolation.

\chapter{Resource and fixture
orchestration}\label{resource-and-fixture-orchestration}

CTest supports \passthrough{\lstinline!FIXTURES\_SETUP!},
\passthrough{\lstinline!FIXTURES\_REQUIRED!},
\passthrough{\lstinline!FIXTURES\_CLEANUP!},
\passthrough{\lstinline!RESOURCE\_LOCK!} and processor or
resource-allocation properties. A fixture models set-up/cleanup around
dependent tests; a resource lock serializes access to a named resource.

\begin{lstlisting}
add_test(NAME db.setup COMMAND db_fixture --start)
add_test(NAME db.query COMMAND query_fixture --check)
add_test(NAME db.cleanup COMMAND db_fixture --stop)
set_tests_properties(db.setup PROPERTIES FIXTURES_SETUP db)
set_tests_properties(db.query PROPERTIES FIXTURES_REQUIRED db RESOURCE_LOCK database)
set_tests_properties(db.cleanup PROPERTIES FIXTURES_CLEANUP db)
\end{lstlisting}

The
\passthrough{\lstinline!db\_fixture!}/\passthrough{\lstinline!query\_fixture!}
commands above are illustrative placeholders, not included executables.
Real suites should make cleanup robust after failed set-up, assign
unique namespaces to parallel jobs and use CI service containers or
dedicated ephemeral test infrastructure where necessary.

\chapter{Negative tests and failure
injection}\label{negative-tests-and-failure-injection}

A negative test asserts that an invalid configuration fails \textbf{for
the expected reason}, rather than merely returning a nonzero exit. For
configure tests, invoke CMake in a temporary binary directory with a
purposely invalid option and inspect a stable diagnostic. For API code,
test edge cases, overflow, invalid input, resource starvation and
cancellation.

\chapter{Static analysis pipeline}\label{static-analysis-pipeline}

The book covers clang-tidy, cppcheck, cpplint and Include What You Use.
These tools are not interchangeable; choose checks based on coding
standard, defect patterns, compiler representation and acceptable
false-positive rates. An external security scanner such as CodeQL
complements these rather than replacing them.

\begin{lstlisting}[language=sh]
cmake -S . -B build/analyze -G Ninja \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build/analyze
# If clang-tidy is installed:
clang-tidy -p build/analyze src/math.cpp
\end{lstlisting}

\begin{lstlisting}
find_program(CLANG_TIDY_EXE NAMES clang-tidy)
if(CLANG_TIDY_EXE)
  set_property(TARGET bsuite_core PROPERTY
    CXX_CLANG_TIDY "${CLANG_TIDY_EXE}")
endif()
\end{lstlisting}

\textbf{Decision:} avoid silently skipping mandatory analysis in CI. If
a tool is required, fail early with a precise diagnostic. A compilation
database is generator-dependent; verify that the analysis sees generated
sources and the same feature defines as the real build.

must reach executable/shared-library link steps. Distinct instrumented
build directories prevent cache and object contamination; check
third-party dependency compatibility and runtime library availability.

\chapter{Coverage methodology}\label{coverage-methodology}

Choose a compatible compiler + coverage toolchain combination. For
GNU-family toolchains, gcov-oriented flags/tooling are common; for
Clang, LLVM's source-based coverage is appropriate when enabled for all
relevant source objects. Capturing a \passthrough{\lstinline!.profraw!}
file alone is not a human-readable report.

\textbf{{[}ENGINEERING EXTENSION{]}} Coverage dimensions:

\begin{itemize}
\tightlist
\item
  Line coverage: exercised source lines / instrumented eligible source
  lines.
\item
  Branch coverage: exercised branch outcomes / instrumented branch
  outcomes.
\item
  Change-based coverage: modified lines exercised in representative
  tests.
\item
  Risk-weighted coverage: critical parser, allocator, privilege-handling
  and boundary logic get stronger test expectations than trivial
  wrappers.
\end{itemize}

A high number can conceal missing edge cases and specification errors.
Combine coverage with mutation tests and input generation where
criticality warrants the cost.

\chapter{CodeQL and secure SDLC
extension}\label{codeql-and-secure-sdlc-extension}

\textbf{{[}ENGINEERING EXTENSION{]}} GitHub CodeQL supports build modes
for compiled languages; as of the referenced GitHub documentation, C/C++
can use \passthrough{\lstinline!none!},
\passthrough{\lstinline!autobuild!} or \passthrough{\lstinline!manual!}
modes. Manual mode makes explicit build commands available to extraction
and is worth evaluating for generated-source-heavy projects. Do not
claim that CodeQL always requires a build or that
\passthrough{\lstinline!none!} necessarily misses all relevant source.
See
\url{https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-for-compiled-languages}
.

Capture code scanning alerts and triage by exploitability and developer
ownership. Associate the verified fix with an independently scanned
change, not just a post-merge status. Run CodeQL in an appropriately
configured workflow; it is \textbf{not} a native CMake command.

\chapter{Test failures: structured
triage}\label{test-failures-structured-triage}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Reproduce} using the failing revision, toolchain, preset and
  generator.
\item
  \textbf{Localize} to configure, compile, link, test assertion,
  environment, install or package phase.
\item
  \textbf{Collect} compiler command, CMake trace/find diagnostics and
  \passthrough{\lstinline!ctest -VV!} as relevant.
\item
  \textbf{Discriminate} product defect from analyzer false positive,
  flaky infrastructure or unsupported platform.
\item
  \textbf{Fix} in target graph or source, add a focused regression,
  rerun relevant cross-platform paths.
\item
  \textbf{Record} evidence, owner, severity, affected versions and
  release disposition.
\end{enumerate}

\chapter{Hands-on practical
assessments}\label{hands-on-practical-assessments}

\textbf{Lab 1:} add a valid and invalid arithmetic test, demonstrate
CTest handling. \textbf{Lab 2:} run two tests with a shared lock and
compare to uncontrolled execution. \textbf{Lab 3:} produce a
compiler-warning report and resolve a real target-owned warning.
\textbf{Lab 4:} isolate an ASan canary in its own Debug profile.
\textbf{Lab 5:} configure a clean installed consumer and demonstrate
failure after deliberately deleting an exported header.

\chapter{Final sign-off}\label{final-sign-off}

A product is test-ready when its tests are deterministic, failures
return meaningful nonzero exit statuses, required instrumentation is not
silently disabled, environment assumptions are recorded, and a clean
external consumer can build from installed artifacts. Test pass counts
without scope, versions and failure evidence do not satisfy release
readiness.
