\textbf{Purpose.} A precise, operational reference for configuring,
generating, building, testing, installing, and packaging target-based
CMake projects. \textbf{Baseline:} examples target CMake 3.25+ and C++17
unless noted. \textbf{Source scope:} the terminology and subject
taxonomy follow Parts I--VII of Craig Scott's \emph{Professional CMake},
20th ed.~This manual is an original synthesis, not a transcript or
substitute for the reference.

\chapter{The system model and
invariants}\label{the-system-model-and-invariants}

\textbf{{[}BOOK-GROUNDED{]}} Treat the CMake suite as a lifecycle: CMake
configures and generates the native build graph, the generated build
tool executes compilation and linking, CTest schedules tests, and CPack
creates distributions. Source trees contain declarative
\passthrough{\lstinline!CMakeLists.txt!} files; separate binary trees
contain \passthrough{\lstinline!CMakeCache.txt!}, generated rules,
intermediary objects and final artifacts. This separation allows several
configurations of the same source tree.

\textbf{{[}ENGINEERING EXTENSION{]}} Treat the generated build graph as
an architecture artifact: every production target has a named owner,
public interface, build-time dependency closure, tested configuration
matrix, install contract and security policy. Configuration is not a
secure trust boundary; execute third-party CMake code only in a
controlled environment.

cmake_minimum_required(VERSION 3.25)

\chapter{Target graph semantics}\label{target-graph-semantics}

The public interface propagates through links to consumer targets. Link
named targets or imported targets rather than hard-coded paths where
possible. \passthrough{\lstinline!ALIAS!} targets provide consistent
names; \passthrough{\lstinline!IMPORTED!} targets represent externally
built artifacts. \passthrough{\lstinline!INTERFACE!} libraries
communicate usage requirements without producing a compiled library;
\passthrough{\lstinline!OBJECT!} libraries provide compiled object reuse
but require deliberate graph design.

\section{Generator expressions}\label{generator-expressions}

Generator expressions such as \passthrough{\lstinline!$<CONFIG:Debug>!},
\passthrough{\lstinline!$<COMPILE\_LANGUAGE:CXX>!} and
\passthrough{\lstinline!$<BUILD\_INTERFACE:...>!} are evaluated in
supported generate/build/install contexts, not as ordinary CMake
variables. The target consuming a generator expression influences its
meaning.

\begin{lstlisting}
target_compile_definitions(parser PRIVATE
  $<$<CONFIG:Debug>:PARSER_DIAGNOSTICS=1>
)
target_compile_options(parser PRIVATE
  $<$<AND:$<CXX_COMPILER_ID:GNU,Clang>,$<CONFIG:Debug>>:-Wall>
)
\end{lstlisting}

\textbf{Caution.} Avoid quoting a list-producing generator expression
incorrectly; preserve related option groups with
\passthrough{\lstinline!SHELL:!} where applicable. Test generated
commands rather than assuming a variable's configure-time value predicts
the final command line.

  target_link_libraries(${name} PRIVATE ${ARG_LIBRARIES})
endfunction()
\end{lstlisting}

\chapter{Variables and control flow}\label{variables-and-control-flow}

A reproducible configuration should have a declared input interface,
sensible defaults, \passthrough{\lstinline!message(STATUS ...)!}
diagnostics and intentionally limited cache exposure. Use
\passthrough{\lstinline!if!}, \passthrough{\lstinline!foreach!},
\passthrough{\lstinline!while!}, \passthrough{\lstinline!block!} and
\passthrough{\lstinline!return!} for configuration logic, never for
runtime business logic.

\begin{lstlisting}
option(BSUITE_BUILD_TESTING "Build test programs" ON)
if(BSUITE_BUILD_TESTING)
  include(CTest)
  if(BUILD_TESTING)
    add_subdirectory(tests)
  endif()
endif()
\end{lstlisting}

\textbf{Decision point.} Use \passthrough{\lstinline!option!} for
user-tunable booleans. Use a target property for per-target state. Use a
preset for developer/CI configurations. Use a toolchain file for
cross-compilation and compiler selection. Do not set compilers inside
\passthrough{\lstinline!CMakeLists.txt!} after
\passthrough{\lstinline!project()!}.

\chapter{Files, custom tasks and generated
artifacts}\label{files-custom-tasks-and-generated-artifacts}

\textbf{{[}BOOK-GROUNDED{]}} Prefer explicit source lists, a
deterministic code-generation command and correct
\passthrough{\lstinline!OUTPUT!}/\passthrough{\lstinline!DEPENDS!}
edges. \passthrough{\lstinline!add\_custom\_command(OUTPUT ...)!}
describes generated files;
\passthrough{\lstinline!add\_custom\_target()!} creates a named
orchestration node.

\begin{lstlisting}
add_custom_command(
  OUTPUT "${CMAKE_CURRENT_BINARY_DIR}/generated/version.h"
  COMMAND "${CMAKE_COMMAND}" -E make_directory
          "${CMAKE_CURRENT_BINARY_DIR}/generated"
  COMMAND "${CMAKE_COMMAND}" -E copy_if_different
          "${CMAKE_CURRENT_SOURCE_DIR}/templates/version.h"
          "${CMAKE_CURRENT_BINARY_DIR}/generated/version.h"
  DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/templates/version.h"
  VERBATIM
)
\end{lstlisting}

Generated outputs must be enumerated and associated with the target that
needs them. Avoid writing into the source tree during builds and avoid
timestamps as proof of correctness. For C++20 module support, validate
compiler, CMake and generator compatibility before adopting a module
file set.

\chapter{Testing and analysis}\label{testing-and-analysis}

CTest tests are registered with
\passthrough{\lstinline!add\_test(NAME ... COMMAND ...)!};
\passthrough{\lstinline!ctest!} schedules selection, parallel execution,
fixtures, resources and reporting. For named test executables, CMake can
substitute their build artifact paths. Distinguish test
\emph{assertions} in the program from test \emph{scheduling} via CTest.

\begin{lstlisting}
include(CTest)
if(BUILD_TESTING)
  add_executable(parser_tests tests/parser_tests.cpp)
  target_link_libraries(parser_tests PRIVATE parser)
  add_test(NAME parser.unit COMMAND parser_tests)
  set_tests_properties(parser.unit PROPERTIES LABELS "unit;smoke" TIMEOUT 20)
endif()
\end{lstlisting}

\begin{lstlisting}[language=sh]
ctest --test-dir build -L unit --output-on-failure --output-junit build/junit.xml
\end{lstlisting}

Static analysis integrations may use
\passthrough{\lstinline!CMAKE\_CXX\_CLANG\_TIDY!},
\passthrough{\lstinline!CMAKE\_CXX\_CPPCHECK!} and compilation
databases. Sanitizers are compiler/linker instrumentation, not CTest
engines. Coverage tools vary with LLVM versus GCC toolchains; measure
coverage of the test binary, not a claim of fault-detection adequacy.

\chapter{Installation, exported targets and
packaging}\label{installation-exported-targets-and-packaging}

Installable libraries should publish a relocatable package config with
an exported namespace, a version file and public header paths. The
included reference project demonstrates
\passthrough{\lstinline!GNUInstallDirs!},
\passthrough{\lstinline!FILE\_SET HEADERS!},
\passthrough{\lstinline!install(EXPORT ...)!},
\passthrough{\lstinline!configure\_package\_config\_file!} and
\passthrough{\lstinline!write\_basic\_package\_version\_file!}.

\begin{lstlisting}
include(GNUInstallDirs)
install(TARGETS parser EXPORT parserTargets
  ARCHIVE DESTINATION "${CMAKE_INSTALL_LIBDIR}"
  LIBRARY DESTINATION "${CMAKE_INSTALL_LIBDIR}"
  RUNTIME DESTINATION "${CMAKE_INSTALL_BINDIR}"
)
install(EXPORT parserTargets NAMESPACE Parser::
  DESTINATION "${CMAKE_INSTALL_LIBDIR}/cmake/Parser")
\end{lstlisting}

This snippet is illustrative: a consumable package also requires a
package configuration file, correct header installation and dependency
discovery. Never hard-code source/build machine absolute paths into an
installed export. CPack consumes installation rules; it does not
determine whether runtime dependencies, ABI compatibility, security
fixes or licenses have been handled.

\chapter{Normative engineering
checklist}\label{normative-engineering-checklist}

\begin{itemize}
\tightlist
\item[$\square$]
  Pin and document minimum CMake version, compiler requirements and
  generators.
\item[$\square$]
  Keep source trees free of build outputs; configure distinct build
  directories.
\item[$\square$]
  Model all public dependencies through usage requirements.
\item[$\square$]
  Have at least one clean, installed-consumer smoke test.
\item[$\square$]
  Execute CTest with deterministic selections and machine-readable
  results.
\item[$\square$]
  Document toolchain constraints, package provenance and build
  reproducibility limits.
\item[$\square$]
  Run static analysis and runtime instrumentation in complementary CI
  jobs.
\item[$\square$]
  Review every new external dependency and CMake configuration script as
  executable code.
\end{itemize}
