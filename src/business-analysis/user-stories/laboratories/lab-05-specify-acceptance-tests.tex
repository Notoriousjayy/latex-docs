\section{Scenario and initial inputs}
Rules: a requester may view only their own records; missing category prevents submission; successful submission generates one tracking reference; retry after timeout must not duplicate submission.

\section{Procedure}
\begin{enumerate}[leftmargin=*,itemsep=3pt]
\item Write eight concrete given/when/then-style scenarios spanning success, invalid data, security, idempotency and boundaries.
\item Design fixtures with two distinct requesters and clean test data.
\item Assign each scenario to automated or manual verification and identify the oracle.
\item Include one measurable latency constraint with explicit load profile.
\item Create a blank-to-completed evidence example recording build, result and defect linkage.
\end{enumerate}
\section{Submission checklist}
\begin{itemize}[leftmargin=*,itemsep=2pt]
\item Eight scenarios
\item One test matrix and fixture plan
\item A cross-cutting constraint with measurement protocol
\end{itemize}
\section{Verification criteria}
\begin{itemize}[leftmargin=*,itemsep=2pt]
\item Outputs describe user outcomes rather than only technical activity.
\item Evidence is sufficient for another practitioner to reproduce or challenge the work.
\item Security, negative behavior and assumptions are visible when relevant.
\item Explicit tradeoffs and decision rights appear in the results.
\end{itemize}
\begin{tcolorbox}[colback=amberback,colframe=navy,title={Instructor note / expected reasoning},breakable]
Security denial must prove no sensitive record contents are disclosed, not merely a red error message.

\end{tcolorbox}
\section{Stretch exercise}
Exchange artifacts with another participant. Identify one unverifiable expectation, one dependency hidden by the initial plan, and one incomplete traceability link. Revise the record and document what changed.
