\DocProvenance
\section{Conceptual focus}
Reviewing documentation quality is not the same as proving architecture correctness.

\section{Reading map}
Book location: Reviewing an Architecture Document. Principal topics: fit-for-purpose review, artifact scope, question sets, issue resolution. Read the chapter discussion, then its summary checklist and selected discussion questions. Record terms precisely before adapting them to an implementation.

\section{Learning objectives}
\begin{itemize}
\item Explain fit-for-purpose review, artifact scope, question sets, issue resolution in terms of a stakeholder question.
\item Set review purpose, artifact versions, stakeholders, evidence, severity, disposition, and follow-up.
\item Separate book-supported architectural concepts from optional implementation techniques such as Terraform, OpenAPI, and CI-generated evidence.
\end{itemize}
\section{Engineering interpretation}
Set review purpose, artifact versions, stakeholders, evidence, severity, disposition, and follow-up.

\section{Worked laboratory assignment}
Run a review with role-specific questions, capture at least eight actionable findings.

\section{Evidence to submit}
Review record + scored assessment

\section{Review prompts}
\begin{itemize}
\item How do you determine whether the AD is usable by an operator?
\item What relation types or behavior are intentionally outside the scope of this view?
\item Which system change would invalidate your claims, and how would you detect it?
\end{itemize}

\section{Chapter-specific analysis tasks}
\begin{itemize}
\item Identify and define each relevant element and relation before you choose a diagram notation.
\item Produce one counterexample showing how a plausible but incorrect model could mislead a stakeholder.
\item Identify the source and timestamp of at least one fact about the implementation; label inference separately.
\end{itemize}
