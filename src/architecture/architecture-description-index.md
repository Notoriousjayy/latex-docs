# Architecture description index (ISO/IEC/IEEE 42010:2022 alignment)

This index is the compact architecture-description (AD) record for the diagram
corpus of this repository. It applies the concepts of ISO/IEC/IEEE 42010:2022
(second edition, 2022-11; <https://www.iso.org/standard/74393.html>; supplied
full text consulted 2026-09-05) proportionately: architectural collections get
viewpoint specifications and traceability, teaching collections reference a
collection-level specification, and non-architecture diagrams receive
model-kind documentation only. It is **alignment with documented gaps, not a
conformance claim** (see the requirement register at the end).

Machine-readable companions, regenerated by the build tooling:

| Artefact | Command | Content |
| --- | --- | --- |
| Diagram inventory | `python3 tooling/scripts/plantuml_inventory.py --json out.json --markdown out.md` | one row per source and `@startuml` block: stable ID, block/output name, collection, purpose, model kind, C4 level, style entry point, transitive includes, config, output matrix, consumers, subject kind, viewpoint, migration action, render status |
| Render result | `python3 tooling/scripts/latex_build.py render-plantuml --result public/logs/plantuml-render.json` | per-diagram render/format status; the authoritative evidence for "every required output freshly rebuilt" |
| Style lint | `python3 tooling/scripts/plantuml_lint.py` | include-chain, token-discipline and legend rules (executable correspondence methods CM-1..CM-4 below) |

## 3. Viewpoint specifications (cl. 8.1)

Each viewpoint below records: purpose, typical stakeholders, perspectives, concerns, aspects, model kinds and legends, correspondence methods, sources, and construction/review methods. Versions are per this index (v1.0). Model kinds are specified in §3.1; their conventions are the cited notation specifications plus the house presentation rules in `tooling/plantuml/README.md`.

### VP-SOFTWARE-STRUCTURE — software system structure (C4)

- **Purpose**: answer "how does one software system relate to people and neighbouring systems" (context), "what applications and data stores make it up" (container), "what functionality sits inside one container" (component).
- **Stakeholders / perspectives**: ST-1, ST-5 / reference, deployment.
- **Concerns**: C-1, C-10, C-11. **Aspects**: structural, connectivity.
- **Model kinds**: MK-C4-CONTEXT, MK-C4-CONTAINER, MK-C4-COMPONENT.
- **Correspondence methods**: CM-2 (element aliases reused across the views of one system), CM-3 (state tagging).
- **Sources**: <https://c4model.com/diagrams>, <https://c4model.com/diagrams/notation>, <https://c4model.com/diagrams/checklist> (accessed 2026-09-05); C4-PlantUML 2.13.0 (<https://github.com/plantuml-stdlib/C4-PlantUML>).
- **View methods**: construct with the `c4/*-diagram-style.iuml` leaves and `C4_TITLE`; review with the C4 checklist (title states type and scope; every relationship labelled with a verb and, where known, a protocol; "not specified" instead of invented technology; `SHOW_LEGEND()` present).
- **Views**: `src/architecture/diagrams/software-system-container-view.puml`, `src/architecture/enterprise/itsm-cmdb/glpi-itop-integr-arch-itam-cmdb.puml`, framework examples `tooling/plantuml/c4-context-example.puml`, `c4-container-example.puml`.

### VP-PLATFORM-DEPLOYMENT — runtime deployment (C4 deployment / UML deployment)

- **Purpose**: where container instances run in one named environment.
- **Stakeholders**: ST-5, ST-1. **Concerns**: C-10, C-11. **Aspects**: deployment, connectivity.
- **Model kinds**: MK-C4-DEPLOYMENT (application/data-store instances on nodes) or MK-UML-DEPLOYMENT (when artifact/node semantics are the point).
- **Correspondence methods**: CM-2, CM-3.
- **Views**: `src/devops/platform/business-applications/suitecrm/suitecrm-self-hosting-architecture.puml`, `src/devops/platform/identity/authentik/self-hosted-docker-compose-arch.puml`; UML deployment views across the security and cloud collections.

### VP-STYLE-CATALOG — Views-and-Beyond style catalogue (reference patterns)

- **Purpose**: teach module, component-and-connector and allocation styles from *Documenting Software Architectures: Views and Beyond* (Clements et al., 2nd ed.).
- **Stakeholders**: ST-1, ST-2. **Concerns**: C-1, C-2, C-4. **Aspects**: structural (module), C&C, allocation.
- **Model kinds**: the UML model kinds MK-UML-* chosen per diagram (recorded in the inventory); reference-model notation from the book is preserved where it differs from UML (e.g. C&C ports and roles), and the house legend explains role colours.
- **Legend convention**: any diagram using a hidden role stereotype (`<<ok>>`, `<<invalid>>`, ...) carries a legend (executable as CM-4).
- **Correspondence methods**: CM-1, CM-4.
- **Views**: 178 diagrams under `src/architecture/views-and-beyond/style-catalogs/**` (see inventory).

### VP-CLOUD-PATTERN — cloud architecture pattern library

- **Purpose**: illustrate cloud mechanisms and compound patterns (Erl et al. numbering retained in titles).
- **Stakeholders**: ST-1. **Concerns**: C-1. **Aspects**: structural, behavioural (sequence views for failover and relocation).
- **Model kinds**: MK-UML-COMPONENT, MK-UML-DEPLOYMENT, MK-UML-SEQUENCE, MK-UML-PACKAGE.
- **Views**: 51 diagrams under `src/architecture/cloud/**`.

### VP-SECURITY-PROCESS / VP-SECURITY-TEACHING — AppSec processes and teaching examples

- **Purpose**: operational process flows (activity diagrams) and teaching examples including intentionally vulnerable paths.
- **Stakeholders**: ST-1. **Concerns**: C-1, C-2. **Aspects**: behavioural.
- **Model kinds**: MK-UML-ACTIVITY, MK-UML-CLASS, MK-UML-COMPONENT, MK-UML-SEQUENCE.
- **Invalid-case convention**: an intentionally wrong example is tagged `<<invalid>>` and its legend says "intentionally ... (do not implement)" (e.g. `idor-horizontal-escalation-vulnerable-path-vs.puml`).

### VP-ENTERPRISE-INTEGRATION, VP-DELIVERY-PROCESS, VP-FRAMEWORK-EXAMPLE

Collection-level specifications: enterprise operating-model/integration diagrams (MK-UML-PACKAGE, MK-C4-CONTAINER), the CI/CD sequence (MK-UML-SEQUENCE), and the framework examples that serve as executable authoring fixtures for every style family.

## 5. Correspondences and correspondence methods (cl. 6.9)

| ID | Method (rule) | Participating AD elements | Executable? | Status |
| --- | --- | --- | --- | --- |
| CM-1 | Every renderable source includes exactly one leaf style module, reaching `house-tokens.iuml` through the canonical chain; no raw hex, `!theme`, local `<style>` or colour/typography skinparam in sources | all diagram sources ↔ style modules | `plantuml_lint.check_include_contract`, `check_source_style_discipline` | holds (lint clean) |
| CM-2 | Within one depicted system, element aliases are reused across its views (context/container/component/deployment) | C4 views of one system | manual (only one C4 view per system exists so far) | holds trivially; documented gap: no multi-view system yet |
| CM-3 | Current-state facts and target-state proposals are distinguishable: `$tags="proposed"` and header `Status:` | C4 views | manual review | holds for the four C4 sources |
| CM-4 | A view component using a hidden role stereotype carries a legend | sources ↔ legends | `plantuml_lint.check_source_style_discipline` | holds |
| CM-5 | Every static figure reference into a managed `png/`, `svg/`, `jpg/` directory resolves to a rendered output | documents ↔ outputs | `diagram_reference_validator --validate` | holds (48 violations fixed in this migration) |
| CM-6 | Output names follow `@startuml <name>`; no two sources in a directory produce the same output | sources ↔ outputs | `plantuml_inventory.py --check` | holds (0 collisions) |

Known inconsistencies (6.9.1): the Views-and-Beyond C&C catalogue draws ports and connector roles in the book's reference notation rather than UML 11.3.4 ports; this is intentional (the model kind is the book's, not UML) and is recorded per collection rather than "fixed".

## 6. Architecture decisions and rationale (cl. 6.10)

| ID | Decision | Rationale | Alternatives rejected |
| --- | --- | --- | --- |
| AD-1 | One neutral token module (`house-tokens.iuml`) beneath both `uml-base` and `c4-base` | one authoritative definition per shared visual decision; UML and C4 must not inherit each other's skinparams | duplicating the palette in c4-base (drift); making c4-base include uml-base (UML skinparams leak into C4) |
| AD-2 | Consume C4-PlantUML from the pinned jar's stdlib, pin its version in the manifest, forbid URL includes | deterministic offline renders; the version is verified at engine-check time | vendoring upstream files (second copy to maintain); `!includeurl` to a tag (network dependency) |
| AD-3 | Role tokens by meaning (primary/dynamic/ok/caution/invalid/alt/neutral) with fill/deep/line depths; meaning also carried by labels and shapes | grayscale and colour-vision safety; enables the migration of 1576 literals without per-diagram design | per-collection palettes (no coherence); pure grayscale (loses teaching distinctions) |
| AD-4 | Convert four software-architecture diagrams to C4; keep UML and reference-model catalogues in their notation | their questions are C4 questions (containers/deployment); the catalogues' value is the notation they teach | manufacturing four C4 levels per topic |
| AD-5 | `DejaVu Sans` as the house font | "Helvetica" was never installed locally or in CI, so Java substituted silently and lost U+25AF; DejaVu is present on both | keep the logical name (unreproducible glyph coverage) |
| AD-6 | JPEG derived from PNG via ImageMagick, flattened onto paper | the engine has no JPEG writer (`-tjpg` yields PNG); transparency must be flattened deliberately | pretending `-tjpg` works (the previous test asserted this) |
| AD-7 | Sequence-diagram numbering opt-in (`SEQ_AUTONUMBER()`) | 11 of 16 corpus diagrams number messages by hand; implicit autonumber produced double numbering | strip hand numbers from 11 diagrams |
| AD-8 | Extension notation approximated as solid triangle line + `<<extension>>` label | PlantUML has no filled-triangle head in class diagrams; the label carries the distinction and the limitation is stated in the module | keep dashed realization (semantically wrong) |
