\section{Viewpoint purpose}
Define conventions for representing repository security governance, CodeQL metadata, analysis coverage and authorized dismissal decisions. A viewpoint prescribes view construction; it is not a finished view or accepted ADR.


\section{Model kinds}
\begin{itemize}
\item Evidence provenance model: source URI, commit, rule and parser versions, timestamp, E1/E2/E3, unknown states.
\item Trust boundary model: privileged app, discovery collector, untrusted PR data, policy and audit stores.
\item Decision state model: scan state, policy decision, approval, execution and reconciliation.
\item Cross-view correspondence: finding-to-repository-to-owner-to-policy-to-exception-to-reviewer mapping.
\end{itemize}

\section{Semantics}
E1 is direct configuration observation, E2 is versioned inference with uncertainty, E3 is independently corroborated. Do not infer live deployment from workflow relationships or merge eligibility from policy evaluation alone.


\section{Construction rules}
View diagrams must indicate source and scope, date, version, known unknowns, and product behavior versus proposed design. Security mutations require a separate execution boundary; all arrows labeled as reads or writes.


\section{Validation questions}
Is every source revision pinned? Does evidence distinguish access denied from no alerts? Do exception edges bind exact finding identity? Is approval authority different from requester? Does every cross-branch dismissal include explicit caution?


\section*{Document status and provenance}
This document is a proposed reference design. Actual GitHub feature availability, organization policies, approvals, and runtime performance must be independently verified before adoption. The architecture inventory is not proof of vulnerability exploitability or correctness of a dismissal.
