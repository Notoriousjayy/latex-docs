\section*{Operating convention and boundaries}
An AICPA criterion identifies an outcome against which controls may be evaluated. The selected point-of-focus headings identify relevant characteristics; they are not discrete certification checklist items. Every owner assignment, technological mechanism and audit test in this suite is a proposed example to be tailored to the system description, commitments, risk profile, period, and service organization responsibilities.

\begin{itemize}
\item Always establish system boundaries, the in-scope trust services categories, service commitments and system requirements first.
\item For a security-only engagement, use the common criteria. For additional trust services categories, include the corresponding additional criteria, subject to properly justified applicability.
\item Document complementary user entity controls and subservice organizations; do not treat vendor assurance reports as replacements for management ownership.
\item Privacy points of focus marked [P] or [C] describe typical processor or controller relevance; assess actual responsibilities rather than treating the annotations as absolute.
\end{itemize}

\chapter{Traceability model}
Traceability is bidirectional: each selected AICPA criterion maps to one or more management controls, and each real operating control can support multiple criteria. Evidence must support the specific assertion being tested, not merely reference the same technology. The rows of this matrix are sample designs, not conclusions about any particular organization.

\subsection{Evidence lifecycle}
\begin{enumerate}
\item Name the control, population and objective before choosing a tool export.
\item Preserve source-system identity, query, scope, period and extraction timestamp.
\item Collect execution artifacts and approvals, as opposed to configuration-only evidence for period tests.
\item Protect integrity and access to the evidence repository; redact personal information where necessary without impairing the required audit trail.
\item Document reviewer, review date, conclusion and exception disposition.
\item Link source export, issue ticket and retest to the same control identifier and criterion identifier.
\end{enumerate}

\chapter{Evidence design for a Type 2 reporting period}
\subsection{Population completeness}
For a change-control assertion, start from all deployed changes in the production deployment system, then reconcile to pull requests or change tickets. Starting only from approved PRs systematically omits bypasses. For identity lifecycle, start from an authoritative workforce exit population and reconcile to all relevant identity stores rather than selecting only disabled accounts.

\subsection{Corroboration and completeness}
\begin{itemize}
\item Access: link termination data, IdP session history, app roles, cloud permissions and service-account scope.
\item Change: link production deployment, immutable commit ID, control checks, approval identities and exceptions.
\item Vulnerability: link asset inventory, scanner coverage, findings, remediation or approved exception, and verification.
\item Incident: link detection event, ticket history, responders, communication approvals and recovery validation.
\item Privacy: link record lineage, disclosed recipients, legal basis or consent, decisions, data subject requests and processor notifications.
\item Availability: link backup catalog, protected storage, executed restoration, successful integrity checks and outcome versus contractual objective.
\end{itemize}
