\section{Assessment objective}
Evaluate a bounded system, not a document library. Define asset, environment, controls, applicable obligations, assessor independence, review date, approved exclusions and evidence retention.
\section{Claim--argument--evidence}
For each security objective: claim $\rightarrow$ formal policy $\rightarrow$ implemented mechanism $\rightarrow$ test or proof $\rightarrow$ observed evidence $\rightarrow$ limitations. Evidence must be a retrievable record tied to a revision, not a proposed test or a scanner configuration alone.
\section{Control assessment method}
\begin{enumerate}
\item Select candidate framework domains and determine which actually apply.
\item Record each mapping as \emph{exact verified}, \emph{thematic}, \emph{not applicable} or \emph{pending verification}.
\item Inspect documents, interview owners and test running behavior. Never infer runtime state from the presence of LaTeX sources.
\item Rate: 0=not designed, 1=design documented, 2=implemented with evidence, 3=independently verified; unknown remains unrated.
\item Record critical deficiencies, remediation, residual risk owner, target, verification and review trigger.
\end{enumerate}
\section{Sample control assurance domains}
Identity; least privilege; information flow; cryptographic key lifecycle; supply-chain provenance; code review; logging; detection; response; recovery; change control. Any blocking control deficiency must be evaluated independently of the weighted total.
\section{Standards boundary}
This suite supplies candidate crosswalks, not an official ISO/IEC 27001 statement of applicability, ISO/IEC 15408 product evaluation, or NIST authorization. Consult licensed normative texts and competent independent assessors for official audits.
