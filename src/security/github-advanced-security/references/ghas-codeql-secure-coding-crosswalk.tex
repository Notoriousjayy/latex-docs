\section{Executive Overview}
This document is the governance index for the modular secure-coding standards suite. It intentionally avoids reproducing every rule card verbatim; instead, it provides traceability through the governing architecture:

\begin{center}\textbf{Cross-Language Baseline $\rightarrow$ Language Standard $\rightarrow$ CWE $\rightarrow$ CodeQL $\rightarrow$ Companion Control $\rightarrow$ SSDLC Enforcement}\end{center}

The canonical inventory contains \textbf{97 persistent rule identifiers}: 20 cross-language controls, 69 programming-language overlays, and 8 GitHub Actions workflow controls. A clean CodeQL result does not demonstrate that an application or workflow is secure.

\code{SCS-ALL-CRYPTO-001} & ALL & Cryptography & Critical Control & Applications MUST use current platform cryptographic APIs and cryptographically secure random generators for security-sensitive values; custom cryptographic primitives and obsolete/broken algorithms MUST NOT be used.\\
\code{SCS-ALL-SECRET-001} & ALL & Secrets & Critical Control & Credentials, API tokens, private keys, and other secrets MUST NOT be hard-coded in source or written to logs; repositories SHOULD enable GitHub secret scanning and push protection for supported secret types.\\
\code{SCS-ALL-ERROR-001} & ALL & Error / Exception Handling & High Priority & Security failures MUST fail closed; externally visible errors MUST NOT disclose secrets, credentials, stack traces, filesystem paths, internal queries, or other sensitive implementation details.\\
\code{SCS-ALL-LOG-001} & ALL & Logging / Monitoring & High Priority & Security-relevant events SHOULD be logged with structured fields; untrusted data MUST be encoded for the logging sink and secrets/sensitive payloads MUST NOT be logged.\\
\code{SCS-ALL-FILE-001} & ALL & File / Path Security & High Priority & File operations MUST constrain attacker-controlled paths to an intended root, avoid unsafe symbolic-link/TOCTOU assumptions, use secure temporary-file APIs, and validate archive extraction destinations.\\
\code{SCS-ALL-DESER-001} & ALL & Serialization / Deserialization & Critical Control & Untrusted input MUST NOT be deserialized by APIs that can instantiate arbitrary types or invoke attacker-influenced code; data-only formats and restrictive/safe loaders MUST be preferred.\\
\code{SCS-ALL-NET-001} & ALL & Network Communications & Critical Control & Sensitive or authenticated network traffic MUST use TLS with normal certificate and hostname verification; production code MUST NOT disable or bypass trust validation except through a documented, narrowly scoped exception.\\
\code{SCS-ALL-WEB-001} & ALL & Web Application Security & Critical Control & Web applications MUST use framework protections for contextual output encoding, anti-CSRF where browser credentials are ambient, secure cookies/session handling, constrained CORS, validated redirects, and outbound-request controls against SSRF.\\
\code{SCS-ALL-DEP-001} & ALL & Dependency / Package Security & Critical Control & Dependencies MUST come from approved sources, SHOULD be locked/pinned reproducibly, MUST be reviewed for known vulnerabilities, and MUST be updated or mitigated according to risk; dependency-review gates SHOULD protect pull requests where available.\\
\code{SCS-ALL-RESOURCE-001} & ALL & Resource Management & High Priority & Untrusted inputs MUST be bounded before allocation, decompression, regex evaluation, recursion, parsing, fan-out, or other resource-amplifying work; services SHOULD enforce timeouts and quotas.\\
\code{SCS-ALL-CONC-001} & ALL & Concurrency / Parallelism & High Priority & Shared mutable state MUST use language-appropriate synchronization/ownership mechanisms; security decisions MUST NOT rely on filesystem or shared state remaining unchanged between separate check and use operations.\\
\code{SCS-ALL-DYN-001} & ALL & Dynamic Code Execution & Critical Control & Untrusted data MUST NOT reach eval-like APIs, runtime code generation, dynamic loaders, reflective invocation targets, or interpreters unless constrained by a purpose-built parser and explicit allowlist.\\
\code{SCS-ALL-FFI-001} & ALL & Native / Foreign Interfaces & Critical Control & FFI/native boundaries MUST be treated as unsafe trust boundaries: signatures, ownership, lifetime, nullability, buffer lengths, thread-safety, and error conventions MUST be validated and documented; a safe wrapper SHOULD isolate raw calls.\\
\code{SCS-ALL-BUILD-001} & ALL & Compiler / Build Security & High Priority & Builds MUST use supported toolchains, fail on security-relevant static-analysis findings according to policy, preserve reproducible dependency state where the ecosystem supports lockfiles, and SHOULD run language-native security diagnostics/tests in CI.\\
\code{SCS-C-MEM-001} & C & Memory Safety & Critical Control & Pointer arithmetic, array indexing, copy operations, and allocation sizes MUST be proven within valid object bounds before use.\\
\code{SCS-C-MEM-002} & C & Memory Safety & Critical Control & Allocated objects MUST have a single, auditable ownership/lifetime model; code MUST NOT dereference or free storage after its lifetime ends and MUST NOT free the same allocation twice.\\
\code{SCS-C-INPUT-001} & C & Input Validation & High Priority & Numeric sizes, offsets, indices, and conversions derived from untrusted input MUST be checked before arithmetic, narrowing conversion, allocation, indexing, or copy operations.\\
\code{SCS-C-OUTPUT-001} & C & Output Encoding & High Priority & Format strings passed to printf-family or equivalent variadic formatting functions MUST be compile-time constants or otherwise trusted; untrusted text MUST be passed as data arguments.\\
\code{SCS-C-FILE-001} & C & File / Path Security & High Priority & Security checks on filesystem objects MUST be coupled to the opened handle where possible; separate path checks followed by later path use MUST NOT be treated as stable authorization.\\
\code{SCS-C-BUILD-001} & C & Compiler / Build Security & High Priority & CI SHOULD include compiler diagnostics at a project-approved strict level plus memory/undefined-behavior instrumentation in dedicated test jobs where the selected toolchain supports it.\\
\code{SCS-CPP-MEM-001} & CPP & Memory Safety & Critical Control & Owning resources SHOULD use RAII and standard ownership abstractions; raw pointers/references SHOULD be non-owning unless an explicitly reviewed invariant requires otherwise.\\
\code{SCS-CPP-MEM-002} & CPP & Memory Safety & Critical Control & Code MUST respect object, reference, iterator, and view lifetimes; references/iterators/views MUST NOT escape beyond the lifetime or mutation rules of their backing object.\\
\code{SCS-CPP-INPUT-001} & CPP & Input Validation & High Priority & Signed/unsigned conversions, narrowing conversions, container sizes, and arithmetic used for allocation/indexing MUST be range-checked before use.\\
\code{SCS-CPP-FFI-001} & CPP & Native / Foreign Interfaces & Critical Control & C APIs, variadic functions, raw allocation APIs, and ABI boundaries MUST be isolated behind typed wrappers that document ownership, lengths, nullability, and error behavior.\\
\code{SCS-CPP-CONC-001} & CPP & Concurrency / Parallelism & High Priority & Shared mutable state MUST be synchronized with standard concurrency primitives; lifetime and ownership MUST remain valid across asynchronous tasks and threads.\\
\code{SCS-CPP-BUILD-001} & CPP & Compiler / Build Security & High Priority & CI SHOULD combine CodeQL with strict compiler diagnostics and sanitizer/instrumented test configurations supported by the project toolchain.\\
\code{SCS-CSHARP-DESER-001} & CSHARP & Serialization / Deserialization & Critical Control & Applications MUST NOT use BinaryFormatter for data processing and MUST NOT treat a binder or configuration switch as making BinaryFormatter deserialization safe.\\
\code{SCS-CSHARP-CRYPTO-001} & CSHARP & Cryptography & Critical Control & Security-sensitive random values MUST use RandomNumberGenerator or an appropriate higher-level .NET cryptographic API; System.Random MUST NOT be used for tokens, keys, salts, or nonces.\\
\code{SCS-CSHARP-FFI-001} & CSHARP & Native / Foreign Interfaces & Critical Control & unsafe code and P/Invoke MUST be isolated, minimized, and reviewed as native trust boundaries with explicit buffer, lifetime, encoding, and ownership contracts.\\
\code{SCS-CSHARP-WEB-001} & CSHARP & Web Application Security & Critical Control & ASP.NET Core applications using cookie-authenticated state-changing requests MUST use the framework anti-forgery mechanisms where the request pattern is CSRF-relevant.\\
\code{SCS-CSHARP-AUTHZ-001} & CSHARP & Authorization & Critical Control & ASP.NET authorization MUST be enforced with server-side policies/handlers at protected endpoints and resources; UI visibility MUST NOT be treated as authorization.\\
\code{SCS-CSHARP-DYN-001} & CSHARP & Dynamic Code Execution & Critical Control & Untrusted data MUST NOT determine dynamically loaded assemblies/types, reflection targets, expressions, or process command strings without strict allowlisting and structured APIs.\\

\code{SCS-JAVA-INPUT-001} & JAVA & Input Validation & High Priority & Inputs crossing trust boundaries MUST be validated before reflection, class/resource lookup, filesystem, XML, regex, allocation, or security-sensitive API use.\\
\code{SCS-JAVA-RESOURCE-001} & JAVA & Resource Management & High Priority & Untrusted sizes, compressed payloads, regexes, XML, object graphs, and other potentially amplifying inputs MUST have application-specific resource limits.\\
\code{SCS-JAVA-FFI-001} & JAVA & Native / Foreign Interfaces & Critical Control & JNI/native integrations MUST validate all lengths, nullability, ownership, thread, exception, and lifetime assumptions at the boundary.\\
\code{SCS-JAVA-DEP-001} & JAVA & Dependency / Package Security & High Priority & Third-party libraries/frameworks MUST be inventoried, security updates tracked, and vulnerable versions remediated or formally mitigated.\\
\code{SCS-KOTLIN-INPUT-001} & KOTLIN & Input Validation & High Priority & External data MUST be validated at runtime; Kotlin type declarations and casts MUST NOT be treated as validation of network, file, database, or deserialized input.\\
\code{SCS-KOTLIN-MEM-001} & KOTLIN & Memory Safety & High Priority & The not-null assertion operator (!!) SHOULD NOT be used on untrusted or platform-typed values unless a prior invariant check proves non-nullness.\\
\code{SCS-KOTLIN-FFI-001} & KOTLIN & Native / Foreign Interfaces & Critical Control & Kotlin/JVM code calling Java/native APIs MUST adopt the callee's security contract, including nullability, serialization, reflection, JNI, and exception behavior.\\
\code{SCS-KOTLIN-DEP-001} & KOTLIN & Dependency / Package Security & High Priority & Projects MUST track supported Kotlin release lines and current dependency security status; unsupported or vulnerable runtime/library versions MUST be upgraded or formally mitigated.\\
\code{SCS-KOTLIN-DESER-001} & KOTLIN & Serialization / Deserialization & Critical Control & JVM deserialization and third-party serialization libraries used from Kotlin MUST follow the same untrusted-input restrictions as Java; arbitrary-object deserialization MUST NOT accept untrusted payloads.\\
\code{SCS-JS-DYN-001} & JS & Dynamic Code Execution & Critical Control & Untrusted strings MUST NOT be passed to eval, Function constructors, dynamic code loaders, template compilation, or equivalent executable sinks.\\
\code{SCS-JS-INPUT-001} & JS & Input Validation & High Priority & When copying or merging untrusted object properties, dangerous prototype-related keys MUST be rejected or the application MUST use data structures/APIs that do not mutate object prototypes.\\
\code{SCS-JS-INJ-001} & JS & Injection Prevention & Critical Control & Node.js child processes MUST use executable/argument APIs without shell interpretation for untrusted arguments; shell strings MUST NOT contain untrusted data.\\
\code{SCS-JS-WEB-001} & JS & Web Application Security & Critical Control & Browser/server JavaScript MUST keep untrusted data out of unsafe HTML/DOM/script sinks and use framework/context-aware escaping APIs.\\
\code{SCS-JS-RESOURCE-001} & JS & Resource Management & High Priority & Node.js network services MUST bound request body sizes, timeouts, socket/connection use, regex complexity, and other attacker-controlled resource costs.\\
\code{SCS-JS-DEP-001} & JS & Dependency / Package Security & Critical Control & Package installation in CI MUST use committed lockfiles and controlled registries; package lifecycle scripts and dependency updates SHOULD be reviewed according to project supply-chain policy.\\
\code{SCS-TS-INPUT-001} & TS & Input Validation & High Priority & Values from untrusted runtime boundaries SHOULD enter as unknown (or an equivalent schema-validation boundary), be validated/narrowed, and only then be assigned domain types.\\
\code{SCS-TS-INPUT-002} & TS & Input Validation & High Priority & Type assertions (as T) and non-null assertions (!) MUST NOT be used as substitutes for runtime validation of attacker-controlled values.\\
\code{SCS-TS-BUILD-001} & TS & Compiler / Build Security & High Priority & Security-sensitive TypeScript projects SHOULD enable strict; exceptions to strict-family checks SHOULD be explicit and reviewed.\\
\code{SCS-TS-DYN-001} & TS & Dynamic Code Execution & Critical Control & Type safety MUST NOT be assumed to mitigate JavaScript runtime injection; TypeScript code MUST follow the JavaScript dynamic-execution, DOM, command, and prototype-pollution controls.\\

\section{Exception Governance}
Every exception MUST be time-bounded and include at least: Rule ID; repository/system; owner; business justification; technical rationale; assessed risk; compensating controls; approver; creation date; expiration date; and remediation plan. Expired exceptions MUST NOT silently remain effective.

\begin{callout}{High}
\textbf{Required lifecycle.} Request $\rightarrow$ security/engineering review $\rightarrow$ approval $\rightarrow$ compensating control verification $\rightarrow$ periodic review $\rightarrow$ expiration or remediation.
\end{callout}

\section{Maintenance and Versioning}
Revalidate this suite when the CodeQL bundle changes; GitHub adds/removes/changes language support; query suites or metadata change; CWE mappings are revised; supported language/platform versions change; or an authoritative secure-coding source is materially updated. Preserve persistent rule IDs when the underlying control intent is unchanged. When a factual correction changes scope or implementation guidance, document the maintenance note and update all affected standalone standards and the master crosswalk from the same canonical inventory.
