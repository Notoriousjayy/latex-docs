\section{Goal}
Design a custom SAST rule with verifiable intent, negative tests and expected false-positive modes. Distinguish lexical rules from AST/semantic and dataflow rules.
\section{Rule design case}
Detect instances of a Python subprocess invocation with \texttt{shell=True} when any portion of the command string can depend on an external request. A lexical detector that flags every \texttt{shell=True} is a useful screening aid, but is not equivalent to proving attacker influence.
\section{Rule specification}
\begin{tabularx}{\linewidth}{@{}p{0.25\linewidth}Y@{}}\toprule
Field & Content required\\\midrule
Rule ID & Stable, namespace-qualified identifier\\
Weakness class & CWE-78 or better-justified CWE, scope assumptions\\
Trigger & Syntax/API construction, source origins and sink argument\\
Exclusions & Trusted constants and validated cases with reasoned guarantees\\
Remediation & Argument-list call or safe in-process API, with proof obligations\\
Evidence & Rule fixture corpus and scanner version\\\bottomrule
\end{tabularx}
\section{Test fixtures}
Provide at least two true positives (direct request input; indirect wrapper), three false-positive guards (constant command, benign shell use with restricted input, unrelated function named \texttt{run}) and two expected limitations (dynamic alias, unresolved library wrapper). Pin the expected output identifiers. Validate that the rule does not simply detect any use of \texttt{subprocess}.
\section{Operationalization}
Run the rule against the fixture corpus; store expected SARIF results, review any noisy rules, and document release criteria for enabling as a PR gate. Do not promote a pattern-only rule to blocking policy solely on one example. Record ownership and scheduled rule regression.
