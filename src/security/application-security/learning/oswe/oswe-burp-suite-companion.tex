\section{Purpose and Relationship to the Curriculum}

This companion follows the curriculum's exact 24-week sequence. It does not
replace the source-review, debugger, database, browser, process, or reporting
work. Its purpose is narrower: use Burp Suite to preserve the network-visible
portion of an evidence chain and to answer a question already justified by
architecture or source evidence.

The operating sequence is:
\begin{enumerate}
  \item reconstruct the application and define scope;
  \item trace attacker influence to a security-sensitive decision or sink;
  \item state a falsifiable hypothesis and its required state;
  \item capture a clean baseline message;
  \item make the smallest meaningful mutation;
  \item compare semantic behavior, not only status or length;
  \item correlate the result with source and independent runtime evidence;
  \item establish practical preconditions, capability, limits, and cleanup;
  \item preserve a final clean-state transcript; and
  \item retest the root-cause fix and alternate paths.
\end{enumerate}

\begin{insightbox}
Burp is most valuable when it records the boundary between a source-derived
hypothesis and an observed runtime path. A Repeater response, scanner issue, or
Collaborator interaction is not independently sufficient. The reviewer still
has to prove that the scoped application produced the observation through the
reviewed code path, under the recorded identity and configuration.
\end{insightbox}

\begin{warningbox}
Use this companion only for systems the learner owns, deliberately vulnerable
training targets, official authorized labs, or systems covered by explicit
written permission. Use synthetic accounts and inert markers. Apply target
allowlists, default-deny egress, request and payload ceilings, clean snapshots,
and documented cleanup. Stop when target identity, state, or effect is ambiguous.
\end{warningbox}

\section{Laboratory Proxy and Browser Setup}

\subsection{Workstation baseline}

\begin{procedurebox}[title=Initial laboratory setup]
\begin{enumerate}
  \item Record the written scope, authorized target version, synthetic roles,
    prohibited actions, stop contact, reset identifier, and evidence path.
  \item Start a temporary project in either edition, or a local disk-based
    project in Professional. Never place an active project on an untrusted or
    shared network drive.
  \item Prefer Burp's built-in browser for initial exercises. It is already
    configured for Burp Proxy and avoids installing a laboratory CA into a
    general-purpose browser profile.
  \item For an external browser, create a dedicated profile, direct it to the
    active loopback listener, export and install Burp's CA only in that profile,
    and plan certificate removal after the lab.
  \item In Target, add only the authorized scheme, host, port, and path roots to
    scope. Exclude analytics, identity providers, CDNs, update services, and any
    other third party unless explicitly authorized.
  \item Configure Proxy history and Site Map to show or log in-scope traffic.
    Keep interception off during ordinary navigation; enable it only when a
    specific message must be paused before transmission.
  \item Disable unsolicited live tasks. For Professional, do not start a crawl
    or audit until its exact scope, authentication, resource pool, and stop rule
    are approved.
  \item Capture a health-check request and response, application version or
    commit, synthetic account state, clock, and clean snapshot identifier.
\end{enumerate}
\end{procedurebox}

\subsection{HTTPS certificate-trust procedure}

The built-in browser is the default. When an external profile is required,
confirm that the Proxy listener is active, export the CA from Burp, import it
only into the dedicated profile or its isolated trust store, and verify one
authorized HTTPS host. After the exercise, remove the CA and delete the profile.
Never install the laboratory CA into an enterprise-wide or production trust
store.

\weekheader{1}{Assessment Foundations, Ethics, and HTTP}{I -- Assessment foundations}{12--14}{4}

\weekfield{Curriculum connection}{The curriculum begins with scope, HTTP
precision, state, and evidence provenance. Source review locates bootstrap,
routes, middleware, parsers, sessions, errors, and outbound clients. Dynamic
work captures the same action through browser, proxy, and command-line clients,
then changes one element at a time. \curriculumartifact{Scope statement,
annotated HTTP transcript, endpoint inventory, and mutation harness.}}

\begin{objectivebox}
\begin{itemize}
  \item Configure a loopback listener, dedicated browser, HTTPS trust, and exact target scope.
  \item Annotate method, target, headers, cookies, body, redirect, and response semantics.
  \item Establish a reproducible Repeater baseline and attach a hypothesis identifier.
  \item Mutate one header, cookie, query value, or body field and classify server behavior.
\end{itemize}
\end{objectivebox}

\begin{bridgebox}
\textbf{Source evidence:} route and parser location, middleware order, accepted
content type, and state-creation code. \textbf{Hypothesis:} a named client value
is ignored, normalized, or trusted differently than the code contract suggests.
\textbf{Burp test:} replay the baseline in Repeater and change only that value.
\textbf{Falsifier:} every source-relevant variation reaches the documented
rejection path with unchanged state. \externalproof{Debugger or structured log
showing the selected handler and parsed runtime value.} A status-code difference
without handler and state correlation is insufficient.
\end{bridgebox}

\weekfield{Preflight configuration}{Use the built-in browser or a dedicated
external profile. Confirm the listener, CA trust, scheme/host/port/path scope,
excluded third parties, synthetic account, clean-state ID, maximum request count,
evidence directory, and stop rule. Keep Intercept off until pausing a specific
message is necessary.}

\begin{procedurebox}
\begin{enumerate}
  \item Browse one health endpoint and confirm it appears in HTTP history and Site Map.
  \item Perform a synthetic login and one authenticated action; retain redirects and cookies.
  \item Send the authenticated action to Repeater, name the tab with the hypothesis ID, and add a note.
  \item Send the baseline twice. Record status, meaningful body marker, cookies, redirect target, and timing range.
  \item Mark one attacker-controlled position from the source-derived entry point.
  \item Change only that position; send once and classify reject, ignore, normalize, accept, or ambiguous.
  \item Repeat the same action with \texttt{curl} or the curriculum harness and explain material differences.
  \item Save a sanitized transcript, log correlation, target state, and cleanup result.
\end{enumerate}
\end{procedurebox}

\begin{lstlisting}[caption={Week 1 baseline and one-variable mutation}]
POST /lab/profile HTTP/1.1
Host: app.example.test
Cookie: session=SYNTHETIC-REDACTED
Content-Type: application/x-www-form-urlencoded

displayName=Jordan&theme=light

# Controlled mutation: theme=unexpected
# Expected: documented rejection or normalization
# Falsifying observation: same protected state change under the same handler
\end{lstlisting}

\begin{editionbox}
Proxy, HTTP history, Site Map, message editor, Inspector, Repeater, and Decoder
support the Community workflow. A disk-based project is Professional-only; in a
temporary project, export the sanitized transcript and configuration before exit.
\end{editionbox}

\weekfield{Evidence contribution}{\burpevidence{Exact original and mutated
messages, redirect and cookie transitions, semantic response markers, and a
Repeater note tied to the source path.} These augment rather than replace the
scope statement, endpoint inventory, and mutation-harness logs.}

\begin{troubleshootingbox}
Traffic outside scope, interception left on, a stale cookie, automatic redirect
following, different browser state, implicit content conversion, or several
changed fields can invalidate the comparison. Restore the baseline and reduce
the test to one controlled variable.
\end{troubleshootingbox}

\begin{checkpoints}
The listener and scope are verified; two baseline sends agree; five controlled
mutations have deterministic logs; one transaction maps from socket boundary to
handler; tokens are redacted; and the lab returns to its recorded clean state.
\end{checkpoints}

\weekfield{Reflection}{Which observation was transport behavior rather than
application behavior? What independent evidence proved the handler? Which test
would most quickly falsify the current hypothesis?}

\weekheader{2}{Architecture Reconstruction and Attack-Surface Mapping}{I -- Assessment foundations}{12--15}{3}

\weekfield{Curriculum connection}{Source review inventories routes, workers,
files, parsers, stores, serializers, templates, administration, and outbound
clients. Burp reconciles this source-derived model with deployed HTTP traffic
without assuming that every defined route is reachable. \curriculumartifact{Architecture
model, endpoint/role matrix, trust-boundary register, and prioritized backlog.}}

\begin{objectivebox}
\begin{itemize}
  \item Define exact scope and produce a clean, role-aware Site Map.
  \item Map observed messages to source routes and disposition every mismatch.
  \item Separate public, authenticated, administrative, and internal-only surfaces.
  \item Use crawl or content discovery only within an approved resource pool and stop rule.
\end{itemize}
\end{objectivebox}

\begin{bridgebox}
\textbf{Source evidence:} route declarations, deployment flags, virtual hosts,
static mappings, client calls, and background entry points. \textbf{Hypothesis:}
a source-defined route is deployed under a specific state, or an observed path
maps to an unmodeled handler. \textbf{Burp test:} navigate manually, filter the
Site Map by scope, and issue a non-destructive reachability request. \textbf{Falsifier:}
the deployed configuration excludes the route or all allowed states produce a
documented non-reachable result. \externalproof{Container routing, server access
log, or framework route dump.}
\end{bridgebox}

\weekfield{Preflight configuration}{Create include rules at the narrowest path
root and exclude logout, destructive actions, large downloads, third-party
hosts, and state-changing administrative routes. Prepare synthetic roles and a
rate-limited resource pool. Record whether only manual navigation, a crawl, or a
content enumerator is authorized.}

\begin{procedurebox}
\begin{enumerate}
  \item Import the source route inventory into a worksheet; do not automatically request it.
  \item Browse one functional path per synthetic role and label the resulting Site Map nodes.
  \item For each observed route, record method, content type, role, object, response type, and handler.
  \item For each source-only route, verify deployment configuration before sending a minimal request.
  \item For each runtime-only route, use response and server evidence to identify its handler or proxy rule.
  \item If Professional crawling is permitted, constrain start URLs, authentication, request rate, and excluded paths; review discoveries manually.
  \item Assign each discrepancy a disposition: deployed, disabled, alternate host, state-dependent, framework-generated, background-only, or unresolved.
  \item Freeze the map and rank candidates by attacker access, privilege, parser complexity, and consequence.
\end{enumerate}
\end{procedurebox}

\begin{editionbox}

  \item Disable instrumentation and confirm the fix with a browser regression test.
\end{itemize}
\end{objectivebox}

\end{bridgebox}

\begin{procedurebox}
\begin{enumerate}
  \item Reproduce the client behavior without instrumentation and record navigation and interaction.
  \item Enable DOM Invader, reload, open DevTools, and record the unique canary.
  \item Inject only into source categories justified by the source inventory.
  \item Exercise the required interaction and inspect reported sink, context, and stack trace.
  \item Set breakpoints at source, branch, and sink; record decoded runtime values.
  \item Use an inert visual or console marker to confirm context without external communication.
  \item Replace the unsafe sink or validate and encode for the exact context; add an automated browser test.
  \item Disable DOM Invader, reload a clean profile, and rerun the regression path.
\end{enumerate}
\end{procedurebox}

\section{Burp Procedures for Cumulative Assessments}
\label{sec:assessments}

Burp must reduce uncertainty during an assessment, not create an archive that
cannot be reviewed. Use the same four evidence states throughout:
\emph{discovery}, \emph{candidate}, \emph{final}, and \emph{closed}. Promote a
message to final only after source correlation, a falsifying control, semantic
verification, clean-state reproduction, and cleanup.

\section{Supplemental Burp Suite Workflows}

These workflows are optional. They do not add weeks, change readiness thresholds,
or increase the required 12--15-hour weekly workload. Use them only when they
reinforce a curriculum competency or a scoped application exposes the feature.

\subsection{JSON Web Tokens}
\begin{optionalbox}
\textbf{Reinforces:} Weeks 5--7 identity, session, and authorization analysis.
Trace token creation, algorithm/key selection, claims, audience, issuer, expiry,
revocation, and server policy before editing. Capture a valid synthetic token,
decode only to inspect representation, change one source-derived property, and
verify protected server behavior. An extension may simplify viewing or signing
laboratory fixtures, but requires code, permission, key-handling, and data-flow
review. Decoding claims does not validate authenticity, and an altered token
accepted by a client is not proof of server acceptance.
\end{optionalbox}

\subsection{Cross-Origin Resource Sharing}
\begin{optionalbox}
\textbf{Reinforces:} Weeks 7, 17, and 18 trust and browser analysis. Map origin
parsing, allowlist logic, credential mode, preflight handling, caching, and
sensitive response paths. Replay a synthetic request with one controlled Origin,
then confirm actual browser readability under the required credentials. An
\texttt{Access-Control-Allow-Origin} header alone is insufficient without browser,
credential, and sensitive-response evidence.
\end{optionalbox}

\subsection{GraphQL}
\begin{optionalbox}
\textbf{Reinforces:} Weeks 2, 7, and 8 attack-surface, policy, and logic analysis.
Derive schema, resolvers, data loaders, authorization, batching, depth/complexity,
and error behavior from source. Use Repeater to send a minimal valid query and
change one field, object, alias, or role at a time. Avoid broad introspection or
resource-heavy queries unless explicitly authorized. Prove resolver-level policy
and final synthetic object access.
\end{optionalbox}

\subsection{Clickjacking}
\begin{optionalbox}
\textbf{Reinforces:} Weeks 7 and 17 browser trust. Identify sensitive state-changing
pages, anti-CSRF behavior, frame policy, SameSite behavior, and user interaction.
Use an inert local framing page or current Clickbandit tooling where available.
Do not present a visual overlay as sufficient evidence: confirm the page can be
framed, the synthetic user can complete the action, and server-side protections
do not prevent the consequence.
\end{optionalbox}

\subsection{HTTP Parameter Pollution and Verb Tampering}
\begin{optionalbox}
\textbf{Reinforces:} Weeks 1, 3, 7, and 8 parser and policy reasoning. Determine
how every proxy, framework, and application layer handles duplicate names, order,
arrays, query/body conflicts, and method overrides. Use Repeater to add one
duplicate or alternate method while preserving state, then record the value and
method seen at each boundary. A response difference is not enough; prove the
security decision used a different interpretation.
\end{optionalbox}

\subsection{Path Traversal and File Inclusion}
\begin{optionalbox}
\textbf{Reinforces:} Weeks 3, 11, and 12 path and interpreter analysis. Trace
decoding, canonicalization, base-directory enforcement, include/load semantics,
permissions, and response behavior. Use only a synthetic marker file inside the
lab. Test one source-derived representation at a time and distinguish file read,
file selection, server-side include, and code interpretation. Never access host
secrets or deliver an active file.
\end{optionalbox}

\subsection{Client-Side Resource Manipulation}
\begin{optionalbox}
\textbf{Reinforces:} Weeks 17--19 browser data flow. Trace controlled URLs,
message data, DOM assignments, script/style/image loads, CSP, integrity, and
origin. Use a lab-local inert resource and confirm the runtime request and consumer.
Do not use an external tracking or exfiltration endpoint.
\end{optionalbox}

\subsection{Extension-Assisted Workflows}
\begin{optionalbox}
\textbf{Reinforces:} Week 4 tool discipline and Weeks 21--24 evidence quality.
Install an extension only when it answers a defined question better than the
manual workflow. Record version, source, code-review result, runtime, traffic
access, project access, network behavior, settings, order, edition dependency,
manual alternative, and known evidence limits. Third-party code can process
sensitive traffic and run arbitrary logic; store review does not remove the need
for independent review and lab-only evaluation.
\end{optionalbox}

\section{Extension Evaluation and Trust Checklist}

\begin{itemize}[label=$\square$]
  \item The extension answers a named assessment question and has a documented manual alternative.
  \item Distribution channel, maintainer, version, release date, source repository, and license are verified.
  \item Source code and dependencies are reviewed for network calls, file/process access, telemetry, and secrets handling.
  \item Required runtime and Burp version are compatible with the isolated workstation.
  \item Traffic, project, cookie, token, issue, and configuration access are documented.
  \item External services and data destinations are blocked or explicitly authorized.
  \item Edition and paid-service dependencies are documented without assuming availability.
  \item Extension-generated findings have defined false-positive and false-negative limits.
  \item Processing order relative to other extensions is recorded.
  \item The extension is tested with synthetic traffic in a disposable project.
  \item Manual reproduction is required before any finding is reported.
  \item The extension is disabled or removed after the relevant exercise.
\end{itemize}

\section{Project Sanitization and Evidence-Export Checklist}

\begin{itemize}[label=$\square$]
  \item Final evidence refers to the reviewed source and target versions.
  \item Only material in-scope messages are included; unrelated discovery traffic is omitted.
  \item Authorization headers, cookies, tokens, credentials, keys, and synthetic secrets are redacted consistently.
  \item Redaction preserves structure needed for reproduction and does not alter the vulnerability-relevant field.
  \item Repeater notes, hypothesis IDs, timestamps, and evidence IDs agree with the report.
  \item Scanner and extension findings are dispositioned; unverified issues are not represented as confirmed.
  \item Collaborator tokens or pending interactions are removed or retired before sharing.
  \item Match/replace rules, macros, session rules, extensions, and configuration affecting final messages are recorded.
  \item Created rows, files, objects, functions, sessions, browser state, and processes are cleaned or documented.
  \item A portfolio copy contains only synthetic or deliberately exposed data.
  \item The original project, if retained, is encrypted and access-controlled; imported project files are treated as untrusted.
\end{itemize}

\section{Glossary}

\begin{description}[style=nextline,leftmargin=1.5em,labelindent=0pt]
  \item[Baseline] Reproducible, clean-state message and semantic result against which one controlled mutation is compared.
  \item[Burp evidence] Network-visible message, configuration, note, timing, or callback record produced or preserved through Burp; it normally requires independent corroboration.
  \item[Callback token] Unique synthetic identifier used to correlate one initiating request with an authorized out-of-band interaction.
  \item[Clean state] Recorded application, database, process, browser, and account condition that can be restored and verified.
  \item[Controllability] Degree to which an attacker can influence a value, type, key, destination, object, sequence, timing, or state at a relevant point.
  \item[Evidence freeze] Point after which no payload, macro, extension, or proof feature changes; only the final clean-state run, cleanup, and reporting proceed.
  \item[Falsifying observation] Result that would disprove or materially weaken the stated hypothesis.
  \item[Marker proof] Harmless, unique, verifiable effect demonstrating a bounded capability without sensitive data access or persistence.
  \item[Message sequence] Ordered HTTP or WebSocket exchanges and state transitions required before the tested operation is meaningful.
  \item[Project setting] Target-specific Burp setting associated with the active project; distinct from workstation-wide user settings.
  \item[Semantic fingerprint] Application-level evidence such as identity, object state, response marker, callback, or effect, rather than status or length alone.
  \item[Session contamination] Accidental reuse or replacement of authentication state across test identities, tabs, profiles, macros, or extensions.
  \item[Source-to-dynamic bridge] Explicit link from source evidence and a falsifiable hypothesis to the smallest Burp test and independent runtime proof.
  \item[Tool lead] Scanner, passive, extension, or differential observation requiring reachability, controllability, impact, and root-cause validation.
\end{description}

\section{Final Burp Readiness Checklist}

\begin{itemize}[label=$\square$]
  \item I can configure a listener, built-in or dedicated browser, HTTPS trust, precise scope, exclusions, and a clean project without assistance.
  \item I can explain project, user, session, task, browser, and extension settings that alter transmitted traffic.
  \item I preserve a stable baseline and state expected and falsifying observations before mutation.
  \item I change one meaningful value, type, identity, object, order, or message field at a time.
  \item I use Intruder only after manual confirmation and enforce request, rate, size, runtime, and state limits.
  \item I interpret Sequencer as statistical support and connect it to source generator evidence and attacker observations.
  \item I isolate identities and can prove authentication, session, and authorization outcomes at protected server operations.
  \item I can correlate SQL, command, file, SSRF, XML, template, and deserialization messages with their actual server boundaries.
  \item I can trace stored and DOM browser data and distinguish response content from live DOM and execution context.
  \item I can preserve a WebSocket handshake, identity, message order, and per-message policy evidence.
  \item I use unique callbacks and distinguish lookup, connection, request, and response access.
  \item I never treat a scanner or extension result as a confirmed finding without manual and source/runtime validation.
  \item I can reproduce every final proof from clean state with safe defaults, semantic verification, bounded failure handling, and cleanup.
  \item I can sanitize messages and manifests without removing the structure necessary for reproduction.
  \item My four cumulative practicals, two mocks, capstone, and readiness thresholds match the curriculum's recorded results.
  \item I understand that completion and green indicators improve preparation but do not guarantee certification success.
\end{itemize}
