\section{Curriculum Overview}

\subsection{Purpose}
This curriculum prepares an experienced practitioner for advanced white-box web
application assessment and the OSWE certification objective. It builds a
repeatable workflow: reconstruct the application, identify trust boundaries,
trace data, form a vulnerability hypothesis, validate it dynamically, construct
a controlled proof of concept, evaluate exploitability, and communicate a fix.

The program is deliberately evidence-driven. A scanner finding is a lead, not a
conclusion. A suspicious function is a candidate point, not a vulnerability. A
runtime anomaly is useful only when it can be connected to reachable code,
attacker control, security impact, and reproducible evidence.

\subsection{Audience and delivery model}
The intended learner already performs application security, penetration testing,
secure code review, software engineering, or vulnerability management. The
recommended pace is 12--15 hours per week: roughly three hours of directed study,
four hours of source review, four to six hours of laboratory work, and one to two
hours of scripting, reporting, and reflection. Delivery may be self-paced or
facilitated; pair review is encouraged for retrospectives, but all graded exploit
and reporting work should be completed independently.

\begin{warningbox}
All offensive activity in this curriculum is limited to systems the learner owns,
deliberately vulnerable training targets, or environments for which explicit
written authorization exists. Laboratories must use synthetic data, inert proof
markers, isolated networks, and reversible snapshots. Never reuse a laboratory
payload, credential, or target configuration against a public or third-party
system.
\end{warningbox}

\subsection{Learning model}
Each topic is treated as a complete assessment loop:
\begin{enumerate}
  \item \textbf{Understand} the relevant protocol, language, framework, and trust model.
  \item \textbf{Inspect} entry points, data transformations, controls, and security-sensitive sinks.
  \item \textbf{Hypothesize} the exact preconditions and bypass needed for exploitation.
  \item \textbf{Validate} with a proxy, debugger, logs, and minimally invasive test input.
  \item \textbf{Automate} only the repetitive portions of a verified manual technique.
  \item \textbf{Report and remediate} the root cause, exploitability, and regression test.
\end{enumerate}

\begin{insightbox}
The 24-week sequence is an instructional synthesis: early weeks create a common
review method; middle weeks apply it to increasingly complex vulnerability
classes; final weeks require integrated, timed performance. Certification-facing
topics receive repeated laboratory exposure, while broader code-auditing material
supplies the reasoning techniques needed for unfamiliar applications.
\end{insightbox}

\section{Program-Level Learning Outcomes}

By the end of the program, the learner will be able to:
\begin{enumerate}
  \item reconstruct an unfamiliar application's architecture and attack surface from source, configuration, traffic, and runtime evidence;
  \item identify trust boundaries and inventory attacker-controlled sources, transformations, controls, and security-sensitive sinks;
  \item perform forward, backward, candidate-point, and hybrid data-flow analysis without depending on scanner conclusions;
  \item analyze authentication, authorization, session, comparison, state, and application-logic decisions for exploitable assumptions;
  \item identify and validate injection, request-forgery, parser, template, upload, deserialization, browser, prototype, and real-time-channel vulnerabilities;
  \item distinguish vulnerability presence from reachability, controllability, exploitability, and material impact;
  \item construct reliable, bounded proof-of-concept scripts with explicit preconditions, safe defaults, verification, and failure handling;
  \item chain compatible weaknesses into an evidence-supported attack path while documenting every dependency;
  \item use static analysis, dynamic analysis, fuzzing, debugging, and proxy tooling as aids to manual reasoning;
  \item recommend root-cause remediation and define regression tests that would detect reintroduction;
  \item preserve evidence and produce concise, technically reproducible vulnerability reports; and
  \item manage time, notes, hypotheses, and recovery decisions during independent, constrained assessments.
\end{enumerate}

\section{Detailed Weekly Curriculum}

\weekheader{1}{Assessment Foundations, Ethics, and HTTP}{I --- Assessment foundations}{12--14}

\weekfield{Rationale}{Advanced exploitation fails when the reviewer cannot
distinguish protocol behavior from application behavior. This week establishes
authorization boundaries, evidence standards, and a precise HTTP vocabulary.}

\weekfield{Prerequisite knowledge}{Basic request/response structure, TCP/TLS
purpose, browser developer tools, and command-line HTTP clients.}

\begin{objectivebox}
\begin{itemize}
  \item Annotate methods, targets, headers, cookies, bodies, status codes, redirects, and encodings in a captured transaction.
  \item Separate client assertions from server-enforced decisions.
  \item Define scope, stop conditions, synthetic-data rules, and evidence-handling requirements for an authorized review.
  \item Reproduce a browser request manually and explain every material difference.
\end{itemize}
\end{objectivebox}

\weekfield{Core concepts}{Arbitrary input, stateless transport and application
state, cookies, content types, origin, TLS termination, proxies, caching,
canonicalization, error behavior, attack surface, trust, and evidence provenance.}

\weekfield{Source-code review focus}{Locate the application bootstrap, route
registration, middleware order, request parsers, session configuration, global
error handlers, and outbound network clients. Mark each point where untrusted
data first becomes a language-level value.}

\weekfield{Dynamic validation focus}{Capture the same action as a browser
request, proxy replay, and command-line request. Change one element at a time and
record whether the server rejects, ignores, normalizes, or accepts the change.}

\weekfield{Required tools or categories}{Intercepting proxy, browser developer
tools, \texttt{curl} or equivalent, source search, structured notes, and version
control.}

\begin{labbox}
\textbf{Guided laboratory.} Trace a login and one authenticated action through
the proxy. Annotate state creation, state presentation, redirects, and error
paths. Correlate each transaction with a route or middleware function.

\textbf{Independent laboratory.} Build an endpoint inventory for a small local
application. Include methods, content types, authentication state, parameters,
response types, and observed error behavior.

\textbf{Exploit-development exercise.} Write a safe request-mutation harness that
can alter one header, cookie, query value, or body field per run; it must log the
exact request, response fingerprint, and exit reason without destructive actions.
\end{labbox}

\weekfield{Deliverable and assessment}{\deliverable{Scope statement, annotated
HTTP transcript, endpoint inventory, and mutation harness.}
\assessment{Ten-question knowledge check plus a 20-minute oral walkthrough of
one request from socket boundary to application handler.}}

\begin{checkpoints}
Completion requires at least 80\% on the knowledge check, a complete evidence
chain for one transaction, and a harness that produces deterministic logs for
five controlled mutations.
\end{checkpoints}

\weekfield{Common mistakes}{Treating HTTPS as proof of application security;
assuming the browser is a trust boundary; changing several variables at once;
omitting redirect or cookie transitions; and collecting traffic without mapping
it to code.}

\weekfield{Defensive and remediation perspective}{Enforce decisions server-side,
parse only expected content types, normalize before validation, fail closed on
ambiguous input, minimize verbose errors, and log security-relevant state changes
without recording secrets.}

\weekfield{Suggested time allocation}{3 hours directed study; 3 hours source
orientation; 4 hours laboratories; 1 hour scripting; 1--3 hours notes and review.}

\weekheader{2}{Architecture Reconstruction and Attack-Surface Mapping}{I --- Assessment foundations}{12--15}

\weekfield{Rationale}{A source-assisted assessment becomes tractable when the
reviewer can explain components, roles, data stores, internal services, and trust
transitions. Mapping prevents both aimless browsing and premature focus on a
single suspicious function.}

\weekfield{Prerequisite knowledge}{Week 1 evidence model, common web tiers,
configuration files, dependency manifests, and basic database concepts.}

\begin{objectivebox}
\begin{itemize}
  \item Reconstruct presentation, business, persistence, messaging, file, and outbound-request components.
  \item Enumerate visible and hidden routes, parameters, asynchronous handlers, and administrative functions.
  \item Identify trust boundaries, privilege identities, internal-only assumptions, and dependency relationships.
  \item Prioritize the attack surface using exposure, privilege, input complexity, and consequence.
\end{itemize}
\end{objectivebox}

\weekfield{Core concepts}{Architecture decomposition, endpoint discovery,
functional paths, role matrices, public versus internal reachability, dependency
trust, deployment configuration, default behavior, attack-surface scoring, and
threat hypotheses.}

\weekfield{Source-code review focus}{Inventory route declarations, controllers,
background workers, scheduled jobs, RPC or WebSocket handlers, template files,
upload directories, database clients, serializer configuration, and environment
variables. Note indirect entry points such as queued data and stored content.}

\weekfield{Dynamic validation focus}{Compare the source-derived inventory with
spidering, content discovery, application navigation, and traffic. Investigate
discrepancies without assuming that a source route is deployed or that an unseen
route is unreachable.}

\weekfield{Required tools or categories}{Source search, dependency and route
inspection, proxy site map, content enumerator configured for the local target,
container/process inspection, and diagramming or structured tables.}

\begin{labbox}
\textbf{Guided laboratory.} Reconstruct a three-tier laboratory application.
Draw components, connections, execution identities, data stores, internal
services, and trust boundaries. Map five HTTP actions to code paths.

\textbf{Independent laboratory.} Find at least three non-obvious entry points
from source or configuration, then determine whether each is deployed, reachable,
authenticated, and authorized.

\textbf{Exploit-development exercise.} Extend the Week 1 harness to import the
route inventory and issue non-destructive reachability probes with rate limits,
authentication profiles, and explicit scope enforcement.
\end{labbox}

\weekfield{Deliverable and assessment}{\deliverable{Architecture model,
endpoint/role matrix, trust-boundary register, and prioritized attack-surface
backlog.} \assessment{A blinded reviewer must be able to locate every listed
entry point and explain the first three priorities from the evidence provided.}}

\begin{checkpoints}
Completion requires at least 90\% agreement between source-derived and
runtime-observed routes in the supplied target, documented disposition of every
discrepancy, and three defensible review priorities.
\end{checkpoints}

\weekfield{Common mistakes}{Equating a route definition with reachability;
missing background or stored-data entry points; ignoring deployment configuration;
failing to record execution identity; and prioritizing only by vulnerability
name rather than attacker access and consequence.}

\weekfield{Defensive and remediation perspective}{Reduce exposed functionality,
remove insecure defaults and unused handlers, separate administrative surfaces,
apply least privilege between tiers, and maintain an accurate application and
data-flow inventory.}

\weekfield{Suggested time allocation}{2 hours study; 4 hours source mapping; 5
hours laboratories; 1 hour scripting; 2--3 hours review and backlog refinement.}

\weekheader{3}{Manual Code Navigation and Data-Flow Analysis}{I --- Assessment foundations}{13--15}

\weekfield{Rationale}{White-box success depends on following meaningful data
through unfamiliar code. This week converts architecture knowledge into a
repeatable review process based on sources, transformations, controls, and sinks.}

\weekfield{Prerequisite knowledge}{Basic control flow, functions and methods,
call stacks, route mapping, and the Week 2 architecture model.}

\begin{objectivebox}
\begin{itemize}
  \item Perform forward, backward, candidate-point, and hybrid traces.
  \item Record branch conditions, transformations, aliases, storage transitions, and trust changes without losing context.
  \item Distinguish validation, canonicalization, sanitization, encoding, and authorization controls.
  \item Decide when a suspicious path is unreachable, uncontrollable, mitigated, or worthy of runtime validation.
\end{itemize}
\end{objectivebox}

\weekfield{Core concepts}{External and internal data flow, taint, candidate
points, call graphs, dependency analysis, variable relationships, control-flow
gates, exceptional paths, persistent storage, implicit conversions, and rereading
code from a second direction.}

\weekfield{Source-code review focus}{Select one request field and trace it to a
security-sensitive operation. Then select a sink and trace backward to every
reachable entry point. Record function, file, variable, type, constraint,
transformation, and unresolved question at each hop.}

\weekfield{Dynamic validation focus}{Use breakpoints or structured logging to
confirm the actual path and runtime value at three trace points. Exercise an error
branch and compare it with the nominal path.}

\weekfield{Required tools or categories}{Fast source search, language server or
code navigator, debugger, call hierarchy, static analyzer, proxy, and a trace
worksheet.}

\begin{labbox}
\textbf{Guided laboratory.} Trace a filename from request input through decoding,
validation, path construction, and file access. Build both forward and backward
traces and reconcile them.

\textbf{Independent laboratory.} Produce three traces: a request-to-database
path, a stored-data-to-template path, and a configuration-to-outbound-request
path. Classify every control encountered.

\textbf{Exploit-development exercise.} Create a trace-driven probe that sends
boundary values chosen from the code's branch conditions and records which path
was reached; do not brute force the input space.
\end{labbox}

\weekfield{Deliverable and assessment}{\deliverable{Three complete source-to-sink
worksheets, debugger evidence, and a candidate-point backlog.}
\assessment{Short code-review practical: identify one reachable weakness and one
false positive in 60 minutes, with explicit reasoning.}}

\begin{checkpoints}
Completion requires correct identification of sources, transformations, controls,
and sinks; runtime confirmation of at least one non-obvious branch; and a clear
reason for closing each false lead.
\end{checkpoints}

\weekfield{Common mistakes}{Searching only for dangerous function names;
discarding type and encoding changes; treating a sanitizer as universal;
stopping at the first validation function; and failing to inspect exceptional or
stored-data paths.}

\weekfield{Defensive and remediation perspective}{Centralize security controls
without obscuring their contracts, use typed APIs, separate canonicalization from
validation, make authorization explicit at the operation boundary, and create
tests for rejected as well as accepted paths.}

\weekfield{Suggested time allocation}{2 hours study; 5 hours tracing; 4 hours
laboratories; 2 hours practical; 1--2 hours retrospective.}

\weekheader{4}{Tool-Assisted Analysis and Practical Assessment I}{I --- Assessment foundations}{13--15}

\weekfield{Rationale}{Tools accelerate a well-formed question. They also create
noise when used without a model. This week integrates fuzzing, static analysis,
dynamic analysis, debugging, and proxy testing into the manual review workflow.}

\weekfield{Prerequisite knowledge}{Weeks 1--3 artifacts, command-line scripting,
debugger basics, and deterministic request replay.}

\begin{objectivebox}
\begin{itemize}
  \item Select a tool based on the evidence needed rather than habit.
  \item Tune a static query or focused fuzzer from a manually verified source/sink hypothesis.
  \item Correlate tool output with source reachability and runtime behavior.
  \item Complete a scoped review from orientation through report under a four-hour time box.
\end{itemize}
\end{objectivebox}

\weekfield{Core concepts}{Tool question/answer contracts, false positives and
false negatives, coverage, instrumentation, fuzz dictionaries from code,
response fingerprints, debugging side effects, evidence correlation, and stopping
rules.}

\weekfield{Source-code review focus}{Identify candidate sinks and branch
conditions, then convert them into one focused static query and one constrained
mutation set. Review dependencies and framework-generated code separately from
application-owned decisions.}

\weekfield{Dynamic validation focus}{Compare proxy replay, debugger state,
application logs, and fuzzer observations for the same test. Explain any mismatch
before expanding the search.}

\weekfield{Required tools or categories}{Intercepting proxy, debugger, static
analyzer or structural search, focused fuzzer, response differ, coverage or
logging instrumentation, and version control.}

\begin{labbox}
\textbf{Guided laboratory.} Start from a manual candidate point. Configure a
static search to find equivalent flows, build a small input dictionary from code
conditions, and validate one result dynamically.

\section{Laboratory Architecture}

The laboratory must be isolated, reproducible, observable, and safe to reset. A
single host may run the components as containers or virtual machines, but the
learner should preserve network boundaries so that internal-only services and
outbound-request behavior remain meaningful.

\begin{longtable}{@{}L{0.17\textwidth}L{0.31\textwidth}L{0.40\textwidth}@{}}
\toprule
\textbf{Zone/component} & \textbf{Purpose} & \textbf{Required controls and observability} \\
\midrule
\endhead
Learner workstation & Browser, proxy, source navigator, debugger, database client, proof development, and reporting & No route to public targets from proof tooling; per-lab allowlists; synchronized clock; encrypted evidence directory; clean browser profiles. \\
Edge/reverse proxy & TLS termination, virtual hosts, routing, headers, and WebSocket upgrade & Access logs, header normalization visibility, explicit trusted-proxy configuration, and no administrative interface exposed outside the lab. \\
Application tier & Multiple deliberately vulnerable services representing PHP, JavaScript/server-side JavaScript, Python or Java, and .NET & Source mounted read-only for review; debugger/log access; distinct low-privilege identities; version-pinned dependencies; health checks and reset scripts. \\

Database tier & Relational database plus PostgreSQL-specific functions, roles, extensions, and large-object exercises & Synthetic records only; distinct application and administrative roles; query logging; volume snapshot; audited extension/function changes. \\

\bottomrule
\end{longtable}

\subsection{Network and data rules}
\begin{itemize}
  \item Default-deny egress from application and learner proof environments. Permit only named laboratory services.
  \item Use reserved private ranges and local test domains. Proof clients must reject all other destinations.
  \item Populate only synthetic identities, tokens, files, database rows, and secrets. Rotate fixtures after each major assessment.
  \item Use marker-based proofs: a known file, log event, database row, callback token, DOM event, or other harmless effect.
  \item Enforce CPU, memory, file-size, recursion, request-rate, and runtime ceilings so malformed inputs cannot destabilize the host.
  \item Separate evidence capture from application logs; redact cookies, authorization headers, and synthetic secrets before portfolio storage.
  \item Test reset before each timed assessment and verify the clean baseline after every chain.
\end{itemize}

\begin{legacybox}
Classic CGI patterns, older server-side platforms, historical browser-extension
models, and legacy application-server defaults remain useful for recognizing trust
mistakes, path confusion, unsafe process invocation, and framework assumptions.
They should be studied as transferable concepts, not treated as a claim about
current platform prevalence. Modern laboratory equivalents should preserve the
underlying trust and parser boundaries.
\end{legacybox}

Use this playbook for weekly labs, cumulative assessments, mocks, and the capstone.
The output of each step becomes evidence or a decision input for the next.

\subsection{Candidate triage questions}
For every candidate path, answer in order:
\begin{enumerate}
  \item \textbf{Presence:} Is the suspicious construct actually in the reviewed version?
  \item \textbf{Reachability:} Can a scoped entry point reach it under a possible state?
  \item \textbf{Controllability:} Which parts of the value, type, timing, object, or destination can the attacker influence?
  \item \textbf{Constraint:} What normalization, validation, authorization, parser, sandbox, permission, or network control intervenes?
  \item \textbf{Exploitability:} Can the required preconditions be met reliably in the deployed environment?
  \item \textbf{Impact:} What new capability is obtained, under which identity, and against which synthetic asset?
  \item \textbf{Evidence:} What source and runtime observations independently support the conclusion?
  \item \textbf{Remediation:} What change removes the root cause, and how will regression be detected?
\end{enumerate}

\section{Vulnerability Analysis Templates}

Every template uses the following mandatory record. Duplicate it for each
candidate rather than combining unrelated paths.

\newcommand{\analysisrecord}{%
\begin{itemize}
  \item \textbf{Assumptions:} architecture, parser, identity, state, deployment, and privilege assumptions that must be verified.
  \item \textbf{Entry points:} route, message, file, stored value, configuration, browser source, or background trigger.
  \item \textbf{Attacker control:} value, type, key, length, timing, object, destination, or sequence the attacker can influence.
  \item \textbf{Transformations:} parsing, decoding, canonicalization, conversion, storage, merge, templating, redirect, or serialization steps in order.
  \item \textbf{Security controls:} validation, authorization, escaping, sanitization, binding, sandbox, integrity, permission, and network controls.
  \item \textbf{Bypass hypotheses:} exact control/interpreter mismatch or missing check; include a falsifying test.
  \item \textbf{Sinks or decisions:} sensitive API, query, process, file, URL, parser, template, object construction, DOM operation, or policy decision.
  \item \textbf{Preconditions:} identity, state, role, configuration, dependency, privilege, timing, interaction, and network requirements.
  \item \textbf{Evidence:} source locations, runtime observations, true/false controls, transcripts, logs, and clean-state rerun.
  \item \textbf{Impact:} new capability, affected synthetic asset, execution identity, scope, reliability, and limitations.
  \item \textbf{Cleanup:} state, file, database, cache, process, token, or browser reset and its verification.
  \item \textbf{Remediation:} root-cause change, defense in depth, regression test, alternate paths, and residual risk.
\end{itemize}}

\begin{tcolorbox}[breakable,title=Template 1 --- Source-to-sink trace,colback=Mist,colframe=Teal]
\analysisrecord
\textbf{Specialized trace prompts:} Record each hop as
\emph{file/symbol $\rightarrow$ variable and runtime type $\rightarrow$
transformation or branch $\rightarrow$ next hop}. Mark trust changes, aliases,
persistent storage, exceptional paths, and unresolved calls. End with a disposition:
confirmed, needs runtime evidence, unreachable, uncontrollable, mitigated, or
out of scope.
\end{tcolorbox}



\begin{tcolorbox}[breakable,title=Template 2 --- Authentication or authorization logic review,colback=Mist,colframe=Teal]
\analysisrecord
\textbf{Specialized logic prompts:} Identify subject, credential/session evidence,
object, operation, workflow state, policy rule, enforcement location, alternate
entry points, failure behavior, and post-decision caching. Test unauthenticated,
owner, non-owner, lower-privilege, higher-privilege, disabled, and invalid-state
synthetic identities as applicable.
\end{tcolorbox}

\begin{tcolorbox}[breakable,title=Template 3 --- Session and token analysis,colback=Mist,colframe=Teal]
\analysisrecord
\textbf{Specialized token prompts:} Capture purpose, format, generator, entropy
inputs, namespace, binding, storage, transport, rotation, idle/absolute expiry,
revocation, replay, logging exposure, privilege change, and recovery behavior.
State what observations an attacker needs and why any prediction or hijacking
claim is practical.
\end{tcolorbox}

\begin{tcolorbox}[breakable,title=Template 4 --- Injection analysis,colback=Mist,colframe=Teal]
\analysisrecord

parameterization, quoting, encoding, regex/character filters, second-order
storage, error or blind oracle, execution identity, and minimal marker. A bypass
must be derived from a documented parser or control mismatch.
\end{tcolorbox}

\begin{tcolorbox}[breakable,title=Template 5 --- File upload and handling analysis,colback=Mist,colframe=Teal]
\analysisrecord
\textbf{Specialized file prompts:} Record multipart parser, client filename,
server name, extension, media type, content inspection, canonical path, temporary
path, final storage, web mapping, access control, downstream processors, archives,
overwrite/race conditions, retrieval headers, and deletion. Compare the validator's
interpretation with every consumer's interpretation.
\end{tcolorbox}

\begin{tcolorbox}[breakable,title=Template 6 --- SSRF analysis,colback=Mist,colframe=Teal]
\analysisrecord
\textbf{Specialized request prompts:} Record URL source, parser, supported schemes,
normalization, user information, host representation, DNS resolution, address
validation, redirect count/revalidation, proxy behavior, connection destination,
ambient credentials, response visibility, callback evidence, and outbound network
policy. Distinguish lookup, connection, request, and response access.
\end{tcolorbox}

\begin{tcolorbox}[breakable,title=Template 7 --- Deserialization analysis,colback=Mist,colframe=Teal]
\analysisrecord
\textbf{Specialized object prompts:} Record format, serializer/deserializer,

\end{tcolorbox}

\begin{tcolorbox}[breakable,title=Template 8 --- Client-side data-flow analysis,colback=Mist,colframe=Teal]
\analysisrecord

least invasive stage that proves material impact. Never infer an edge solely from
the names of two findings.
\end{tcolorbox}

\section{Practical Assessments}
\label{sec:assessments}

Assessment rewards defensible reasoning and reproducibility, not the number of
payloads attempted. A technically interesting result with missing evidence cannot
receive full credit.

\subsection{Recurring assessment cadence}
\begin{itemize}
  \item \textbf{Weekly knowledge check:} 10--15 questions on concepts, code behavior, and false-positive reasoning; target 80\%.
  \item \textbf{Weekly short review:} 30--90 minutes of unfamiliar code or traffic; submit a trace, disposition, or fix test.
  \item \textbf{Artifact review:} The week's diagram, matrix, script, report, or regression test is graded for completeness and reproducibility.
  \item \textbf{Spaced retrieval:} Every weekly check includes at least two concepts from earlier phases.
  \item \textbf{Retrospective:} Record one correct hypothesis, one failed hypothesis, one process change, and one item to revisit.
\end{itemize}

\subsection{Permitted resources and integrity rules}
Learners may use their own notes, local language/framework documentation,
debuggers, source navigators, proxies, and scripts developed during the program.
They may not target systems outside the supplied lab, obtain hints during an
independent assessment, reuse another learner's proof, or present scanner output
as verified evidence. Any third-party snippet incorporated into a proof must be
understood, constrained to the lab, and identified in the private assessment log.

\subsection{Remediation after a failed competency}
Within 24 hours of a score below threshold:
\begin{enumerate}
  \item classify each lost point as knowledge, navigation, data-flow, validation, exploit engineering, reporting, or time-management failure;
  \item select the smallest prior lab that isolates the weak competency;
  \item repeat it from a clean state without viewing the previous solution;
  \item produce a corrected artifact and one new transfer exercise in a different stack;
  \item rerun the failed assessment domain within seven days; and
  \item update the readiness score only when evidence, not confidence, improves.
\end{enumerate}

\section{Capstone Project}
\label{sec:capstone}

\subsection{Scenario}
Conduct an authorized, source-assisted assessment of a deliberately vulnerable
multi-tier application containing browser code, at least two server-side
components, a relational database, file or parser functionality, an internal
service, and a real-time or background-processing path. The learner receives the
scope, source snapshot, synthetic identities, and reset procedure, but not a
vulnerability list.

\subsection{Required work}
The capstone package must:
\begin{enumerate}
  \item reconstruct architecture, execution identities, data stores, trust boundaries, and deployed entry points;
  \item build a prioritized attack-surface and source/sink inventory;
  \item review source using forward, backward, candidate-point, and hybrid strategies;
  \item complete at least five substantive data-flow traces across multiple components;
  \item identify and dynamically validate vulnerabilities with true/false controls;
  \item develop at least one reliable chain of two or more independently verified stages;
  \item provide at least one reusable proof script with scope safeguards, preflight, verification, failure handling, and cleanup;
  \item document at least three unsuccessful hypotheses and the evidence that closed or redirected them;
  \item recommend root-cause fixes and defense-in-depth measures;
  \item apply or inspect at least one selected remediation and demonstrate a regression test; and
  \item produce a professional report, evidence manifest, timeline, and retrospective.
\end{enumerate}

\subsection{Capstone passing and distinction}
Pass requires 80/100, no safety violation, no fabricated or unsupported evidence,

\subsection{Readiness decision}
\begin{itemize}
  \item \textbf{Red:} Any safety/evidence-integrity concern, either mock below passing, capstone below 80, or three or more red indicators. Continue structured remediation.
  \item \textbf{Amber:} All major assessments passed, but one or two red indicators, more than three amber indicators, or an exploit/report requiring material assistance. Schedule focused practice before attempting the objective.
  \item \textbf{Green:} Both mocks at least 85, capstone at least 85, no red indicator, no more than two amber indicators, and every final proof reproduces from clean state without assistance.
\end{itemize}

\begin{warningbox}[title=Readiness limitation]
These indicators measure performance within this curriculum. They do not predict
the exact content of any future assessment and do not guarantee certification
success. Certification objectives, policies, and administrative requirements
should always be confirmed through the current official channel before an attempt.
\end{warningbox}

\subsection{Weekly rhythm}

\subsection{Cornell-style code-review notes}
Use one page per hypothesis:
\begin{itemize}
  \item \textbf{Cue column:} route, sink, security decision, branch question, or unresolved assumption.
  \item \textbf{Evidence column:} source locations, variables/types, transformations, control behavior, runtime observations, and negative controls.
  \item \textbf{Summary:} one sentence each for presence, reachability, controllability, exploitability, impact, and next action.
\end{itemize}
Never paste large source blocks when a file/symbol reference and a focused excerpt
would preserve the reasoning more clearly.

\subsection{Vulnerability hypothesis log}
Assign each hypothesis an identifier and record: timestamp, candidate path, why it
is plausible, expected observation, falsifying observation, test performed, result,
state changes, evidence location, disposition, and next action. Allowed dispositions
are \emph{queued}, \emph{testing}, \emph{confirmed}, \emph{needs evidence},
\emph{unreachable}, \emph{uncontrollable}, \emph{mitigated}, \emph{duplicate},
and \emph{out of scope}.

\subsection{Exploit-development journal}
For each run, record target version, clean-state identifier, proof version, input
summary, preflight result, expected marker, actual marker, request count, elapsed
time, failure category, state changes, cleanup, and evidence directory. Promote a
script to ``final proof'' only after three clean-state runs with the same semantic
result.

\subsection{Tooling discipline}
\begin{enumerate}
  \item State the question the tool should answer.
  \item Record configuration, scope, authentication state, and target version.
  \item Predict the expected result from source or architecture evidence.
  \item Run the smallest useful query or test.
  \item Correlate output with a second evidence source.
  \item Preserve only the material evidence and disposition noise explicitly.
\end{enumerate}

\subsection{Time boxing and stalled investigations}
Use a default 30-minute hypothesis box: 5 minutes to state and rank it, 15 minutes
to inspect or test, 5 minutes to record evidence, and 5 minutes to decide. Extend
only when a new fact materially raises expected value. After three failed
hypotheses in one area, pause and revisit architecture, identity, parser chain,
deployment, or runtime/source mismatch before continuing.

For a stalled path, ask:
\begin{itemize}
  \item Is the entry point deployed and reachable in the current state?
  \item Did parsing change value or type before the code I am reading?
  \item Is there an earlier control or a later interpreter I missed?
  \item Am I testing the same identity, object, and workflow state as the source path?
  \item What observation would falsify the hypothesis quickly?
  \item Is another candidate point higher value for the remaining time?
\end{itemize}

\subsection{Spaced repetition and remediation loop}
Review new material after 1 day, 7 days, 21 days, and during the next cumulative
assessment. Each review must include retrieval from memory, one short code trace,
and one decision about exploitability or remediation. Convert a failed lab into a
remediation card containing: missed cue, incorrect model, correct rule, minimal
practice, transfer exercise, due date, and evidence required to close the card.

\section{Professional Vulnerability-Report Template}

Use one report section per distinct root cause. If multiple symptoms share a root
cause, explain the affected paths without duplicating evidence.

\begin{tcolorbox}[breakable,title=Finding record,colback=white,colframe=Navy]
\begin{tabularx}{\linewidth}{@{}L{0.24\linewidth}Y@{}}
\textbf{Finding title} & Specific weakness and affected operation; avoid sensational language. \\
\textbf{Severity} & Rating, rationale, affected assets, execution identity, scope, reliability, and environmental assumptions. \\
\textbf{Affected component} & Application/service, route or handler, source file/symbol, reviewed version, and configuration. \\

\subsection{Finding quality gate}
Before submission, answer yes to all of the following:
\begin{itemize}
  \item Can a reviewer reproduce the behavior from the stated clean state without oral explanation?
  \item Does every impact statement follow from a verified capability and execution identity?
  \item Are presence, reachability, controllability, exploitability, and impact distinguished?
  \item Are true/false controls and limitations included?
  \item Is the root cause more precise than ``insufficient validation''?
  \item Does remediation remove the unsafe interpretation or missing decision rather than block one observed input?
  \item Is cleanup complete and are credentials, tokens, and synthetic secrets redacted?
\end{itemize}

  \item Evidence manifest complete; credentials/tokens redacted.
  \item Target restored; deviations and irreversible lab state documented.
\end{itemize}

\section{Exploit Reliability Checklist}

\begin{itemize}[label=$\square$]
  \item Target identity, version, scope, and clean-state preconditions verified.
  \item Default mode is dry run or harmless validation; dangerous free-form input is not accepted.
  \item Destinations, identities, objects, message types, and marker operations are allowlisted.

  \item Encodings, content types, parser assumptions, and dependency versions are checked.
  \item Request count, concurrency, timeouts, retries, payload size, and total runtime are bounded.
  \item Success is verified semantically, not only by status code or process exit.
  \item Ambiguous observations cause a stop, not automatic escalation.

  \item Created files, rows, functions, objects, tokens, sessions, and process state are tracked.

  \item Transcript, proof version, target state, and evidence identifiers are recorded.
  \item Three consecutive clean-state runs produce the expected result.
  \item Usage notes state purpose, scope, prerequisites, expected marker, limitations, and cleanup.
\end{itemize}

\section{Glossary}

\begin{description}[style=nextline,leftmargin=1.5em,labelindent=0pt]
  \item[Attack surface] Deployed entry points, handlers, interfaces, data channels, and privileged operations available to a potential attacker.
  \item[Candidate point] Code or configuration worthy of investigation because it may participate in a vulnerability; not itself proof of a finding.
  \item[Canonicalization] Conversion of equivalent representations into a chosen form before a security decision.
  \item[Controllability] The degree to which an attacker can influence a value, type, key, object, destination, sequence, timing, or state at a relevant point.
  \item[Data-flow trace] Evidence-supported path from a source through transformations and controls to a sink or security decision.
  \item[Exploitability] Practical ability to satisfy preconditions and obtain a repeatable security consequence in the deployed context.
  \item[Exploit chain] Two or more independently verified stages in which one stage's capability or artifact satisfies a later stage's precondition.
  \item[False positive] A candidate reported as vulnerable even though required presence, reachability, control, or impact is absent.
  \item[Falsifying test] A test designed to disprove a hypothesis if the expected security condition does not hold.
  \item[Gadget] Existing behavior that converts a controlled condition, such as polluted state or object construction, into a security consequence.
  \item[Marker proof] A harmless, unique, verifiable effect used to establish capability without accessing sensitive data or creating an interactive foothold.
  \item[Reachability] Ability of a scoped entry point and possible program state to execute the candidate code path.
  \item[Sanitization] Transformation intended to remove or neutralize unsafe constructs for a defined grammar and use context.
  \item[Sink] Operation or decision where untrusted influence may cause a security consequence, such as a query, process launch, file access, request, parser, template, deserializer, DOM API, or authorization check.
  \item[Source] Point at which potentially attacker-influenced data or state enters the analyzed system or trust domain.
  \item[Trust boundary] Place where data, identity, privilege, component ownership, or assurance changes and must be re-evaluated.
  \item[Validation] Decision about whether an input satisfies the accepted structure, semantics, range, and policy for a specific use.
  \item[Verification] Independent confirmation that an expected semantic result or cleanup condition occurred.
\end{description}
