\section{Executive summary}

Modern application assurance is a chain of evidence, not a scanner result. Architecture review explains what must be protected; source analysis examines implementation paths before execution; dependency analysis identifies known risk in supported package ecosystems; secret scanning detects credential-like material; interactive application security testing (IAST) observes executed server-side flows; dynamic application security testing (DAST) evaluates a deployed interface from the outside; and manual testing challenges state, roles, and business rules that automation may not understand. NIST frames technical assessment as planning, execution, analysis, and mitigation, while the Secure Software Development Framework (SSDF) places verification and vulnerability response inside the development lifecycle \citep{nist800115,nist800218}.

\begin{keybox}
No individual tool establishes that an application is secure. A defensible conclusion states what was examined, what executed, which roles and workflows were covered, what evidence was produced, and which limitations remain.
\end{keybox}

\section{Scope and applicability}

This methodology applies to web applications, browser clients, HTTP APIs, GraphQL endpoints, microservices, server-side components, cloud-hosted services, supporting repositories, and their declared dependencies. Mobile or thick clients may use the same governance model, but platform-specific testing requires additional controls not defined here.

\subsection{Assessment boundary}

The statement of work or internal authorization record must identify:

\begin{itemize}
  \item application names, repository identifiers, domains, IP ranges, API base paths, environments, and excluded assets;
  \item permitted test types, accounts, roles, transaction classes, and data sets;
  \item branch, release, commit, artifact, and deployment identifiers that bind evidence to a version;
  \item approved testing windows, concurrency limits, source addresses, and monitoring contacts;
  \item prohibited actions, including denial-of-service, destructive state changes, uncontrolled credential attacks, persistence, or access to real customer data;
  \item third-party services and callbacks that require separate authorization;
  \item incident, pause, and emergency-stop procedures.
\end{itemize}

\begin{decisionbox}[Scope decision]
If an asset, endpoint, tenant, integration, or downstream service is not explicitly in scope, treat it as out of scope until the authorization owner updates the record. Configure tools to drop or exclude out-of-scope traffic wherever possible.
\end{decisionbox}

\subsection{Environment selection}

Prefer a production-representative test environment with synthetic data, realistic identity roles, equivalent security controls, observable application health, and a reversible state. Production testing requires an explicit exception, business approval, enhanced monitoring, conservative payloads, and immediate rollback authority. Document every material divergence between the assessed environment and production because the divergence qualifies the conclusion.

\section{Preassessment and information collection}

Preassessment converts an application name into a testable system model. The assessor opens an assessment record before scanning and captures the information below. Gaps become explicit assumptions or blockers, not silent omissions.

\subsection{Intake checklist}

\begin{multicols}{2}
\begin{itemize}
  \checkitem Business purpose and criticality recorded
  \checkitem Data classifications and regulated data identified
  \checkitem Internet and partner exposure documented
  \checkitem Human and machine actors enumerated
  \checkitem Authentication mechanisms and identity providers mapped
  \checkitem Authorization roles and entitlements defined
  \checkitem Test accounts created for every material role
  \checkitem Trust boundaries and privilege transitions diagrammed
  \checkitem Web routes, APIs, events, and administrative interfaces inventoried
  \checkitem OpenAPI, GraphQL, WSDL, or equivalent specifications collected
  \checkitem Repositories, default branches, and generated code identified
  \checkitem Build modes, languages, and package ecosystems recorded
  \checkitem Deployment, runtime, database, queue, and storage technologies recorded
  \checkitem External APIs and callbacks listed with ownership
  \checkitem Sensitive and irreversible workflows identified
  \checkitem Prior findings, risk acceptances, and incidents reviewed
  \checkitem Material changes since the last assessment summarized
  \checkitem Logging, health monitoring, rollback, and emergency contacts tested
\end{itemize}
\end{multicols}

\subsection{Minimum evidence package}

\begin{evidencebox}
The assessment record must bind the application version across layers: repository commit or tag, build artifact identity, deployed release, Seeker project or agent context, InsightAppSec application and scan configuration, and Burp project. If identities cannot be reconciled, report the uncertainty and do not imply end-to-end coverage.
\end{evidencebox}

\section{Architecture review and threat modeling}

The architecture review establishes the security policy that testing will challenge. Start with assets and allowed behavior, then trace data and authority across interfaces. The OWASP ASVS provides testable control requirements; the WSTG provides web testing structure; the API Security Top 10 highlights authorization, resource consumption, inventory, business-flow, and unsafe-consumption risks; and SAMM places threat assessment and architecture assessment within a broader software assurance program \citep{owaspasvs,owaspwstg,owaspapi,owaspsamm}.

\subsection{Review sequence}

\begin{enumerate}
  \item \textbf{Establish objectives.} Define confidentiality, integrity, availability, accountability, privacy, safety, and abuse-resistance requirements.
  \item \textbf{Map actors and assets.} Include users, administrators, services, build identities, secrets, data stores, queues, object storage, and third parties.
  \item \textbf{Trace data and authority.} Mark entry points, transformations, persistence, egress, identity propagation, and privilege transitions.
  \item \textbf{Challenge trust.} Identify implicit trust in clients, headers, tokens, network location, service responses, metadata, package sources, and operational configuration.
  \item \textbf{Examine failure.} Model timeouts, retries, duplicate messages, partial transactions, stale authorization, malformed data, and degraded dependencies.
  \item \textbf{Derive tests.} Convert each credible threat scenario into one or more observable tests with an expected secure result.
\end{enumerate}

\subsection{Risk-based depth}

Increase depth when an application is internet accessible, processes sensitive data, performs high-value transactions, exposes administrative functions, crosses tenant boundaries, brokers identity, invokes privileged downstream services, accepts complex serialized input, or has material change. Depth means more roles, states, negative cases, source-path review, runtime transactions, and manual investigation; it is not simply a longer scanner runtime.

\section{GitHub security assessment procedures}

\subsection{Product and entitlement preflight}

GitHub documents general security features plus paid GitHub Code Security and GitHub Secret Protection capabilities under the Advanced Security portfolio. Public-repository availability differs from private and internal repositories; enterprise-server behavior and versions also differ. Capture platform, plan, product entitlement, repository visibility, security configuration, and the date of verification before asserting coverage \citep{githubfeatures}.

\subsection{Code scanning with CodeQL}

Code scanning is the GitHub alert and workflow capability; CodeQL is the analysis engine used by this runbook. GitHub supports default and advanced setup. Default setup provides a low-maintenance configuration and, for eligible repositories, scans supported languages on pushes to the default or protected branches, qualifying pull requests, and a weekly schedule. Advanced setup is appropriate when the team must control build steps, matrices, triggers, schedules, runners, query packs, or external CI \citep{githubcodesetup}.

\subsubsection{Runbook}

\begin{enumerate}
  \item Inventory active repositories, default and protected branches, languages, generated source, build systems, submodules, and security-relevant code outside the primary repository.
  \item Confirm Code Security entitlement or applicable public-repository availability, then record the security configuration applied to each repository.
  \item Choose default setup unless a documented requirement needs advanced control. For compiled languages, prove that the selected build mode includes the security-relevant targets.
  \item Record analyzed languages, query suite, model packs, custom queries, excluded paths, runner, action or CLI versions, triggers, and schedule.
  \item Require successful analysis on the default branch and on representative pull requests. Investigate missing results, database creation failures, partial builds, timeouts, and tool-status warnings.
  \item Review alert path, source, sink, sanitizer assumptions, locations, commit, analysis origin, and affected behavior. Map the weakness to CWE where appropriate \citep{mitrecwe}.
  \item Link the alert to the owning service and threat scenario. Reproduce safely or corroborate with Seeker, DAST, or manual evidence when exploitability depends on runtime context.
  \item Verify a fix on the remediation branch before merge. Review generated fixes as untrusted code changes and run security, unit, integration, and regression tests.
\end{enumerate}

\subsubsection{Merge protection}

GitHub rulesets can prevent merging when a required code scanning tool reports alerts at configured severities, is still analyzing, or is not configured. The current documented limitations include non-application to merge queue groups and to Dependabot pull requests analyzed by default setup; alert lines must also exist in the pull-request diff \citep{githubmerge}. Treat these limitations as control-design inputs. Where merge protection cannot apply, require an equivalent status check, approval workflow, or post-merge detection with a documented response objective.

\begin{warnbox}[Code scanning is not a completeness claim]
A green workflow proves that the configured analysis completed, not that every language, target, framework, code generator, branch, or security requirement was covered. Retain an explicit coverage inventory beside alert counts.
\end{warnbox}

\subsection{Dependency security}

The dependency graph represents dependencies GitHub can derive from supported manifests and lock files or receive through dependency submission. GitHub can export a repository graph as an SPDX-compatible SBOM. Dependabot alerts compare identified dependencies with advisory data; security updates attempt to raise pull requests for remediable vulnerable dependencies; dependency review exposes package changes and can enforce policy in pull requests \citep{githubfeatures,githubdependencyreview,githubdependabot}.

\subsubsection{Runbook}

\begin{enumerate}
  \item Inventory package ecosystems, manifests, lock files, monorepo directories, private registries, vendored code, binaries, containers, generated artifacts, plugins, and dynamically loaded components.
  \item Confirm dependency graph population and freshness. Use dependency submission when supported build-time resolution is more authoritative, and sequence submission before dependency review to avoid snapshot races.
  \item Reconcile the graph or exported SBOM with build output and deployed inventory. Record unsupported or missing sources as gaps.
  \item Review Dependabot alerts using package, vulnerable range, patched version, advisory identifiers, dependency path, exposure, and application ownership.
  \item Enable security updates when governance permits. Review every pull request for unexpected transitive changes, compatibility, provenance, build integrity, tests, and release notes.
  \item Use dependency review to prevent newly introduced vulnerable packages or prohibited licenses. Align failure thresholds with organizational policy and exception handling.
  \item Determine runtime relevance separately. A present component is not necessarily reachable; a component absent from observed runtime traffic is not necessarily safe.
  \item After remediation, verify the manifest and lock file, regenerate the dependency graph or submission, build the artifact, run tests, and confirm the deployed version.
\end{enumerate}

Dependabot security updates apply to dependencies represented in manifests or lock files; transitive-update behavior varies by ecosystem and available parent upgrades \citep{githubdependabot}. Do not report update automation as full SCA coverage.

\subsection{Secret scanning and push protection}

GitHub secret scanning detects supported credentials in repository content and, depending on product and configuration, can use partner, generic, AI-detected, or custom patterns. Push protection can block supported secrets before repository acceptance. Custom patterns can represent organization-specific formats. Validity checks are available for supported providers and may send a detected secret to the issuer for verification, which requires privacy and policy review \citep{githubsecrets,githubcustompatterns,githubvalidity}.

\subsubsection{Response runbook}

\begin{enumerate}
  \item Treat the alert as a possible credential exposure. Restrict evidence access; do not paste the value into tickets, chat, or reports.
  \item Identify owner, issuer, environment, privileges, expiration, public exposure, commit history, forks, artifacts, logs, and other repositories containing the value.
  \item Revoke or rotate promptly using a coordinated sequence that preserves service continuity. Rotation creates a replacement; revocation invalidates the exposed credential.
  \item Search for unauthorized use through issuer and application logs. Escalate suspected misuse through incident response.
  \item Replace source usage with an approved secret store and short-lived identity where feasible. Remove the value from the active tree and evaluate history rewriting separately.
  \item Confirm the old credential is invalid, the new credential works only where intended, monitoring is complete, and no dependent workflow retains the old value.
  \item Close the alert only with disposition evidence. ``Inactive'' lowers urgency but does not erase the exposure history.
\end{enumerate}

GitHub's remediation guidance emphasizes coordinated revocation and rotation \citep{githubsecretremediation}. Deleting a string from the current file is not credential invalidation.

\subsection{Organization visibility caveat}

Security overview is useful for coverage and portfolio views, but exports have documented omissions. At the verification date, summary exports omit third-party code scanning alerts and certain secret scanning categories, including generic-pattern and ignored-directory alerts \citep{githuboverviewexport}. Build portfolio metrics from APIs or source reports when a summary export cannot represent the required population.

\section{Seeker IAST assessment procedures}

Black Duck describes Seeker as an IAST solution that detects vulnerabilities at runtime while development, DevOps, and QA testing exercise instrumented web applications. Agents run alongside supported application technology, observe runtime behavior, and report analytics to the Seeker server \citep{seekerintro,seekerinstrumentation}. Because support changes by release, obtain the current Agent Technical Specification from the licensed documentation and record exact runtime, framework, platform, agent, and server compatibility before deployment \citep{seekerfeatures}.

\subsection{Deployment and readiness}

\begin{enumerate}
  \item Create or select the Seeker project and bind it to application, release, environment, owner, and assessment record.
  \item Verify server topology, license, roles, data retention, encryption, network paths, proxies, certificates, and capacity. The official installer supports evaluation, deployment, and upgrade modes; follow the current platform-specific guide \citep{seekerinstall}.
  \item Select the agent documented for the exact runtime and framework. Do not infer compatibility from a related runtime.
  \item Deploy only in an approved environment. Record agent configuration, process or container identity, image or package version, project mapping, startup logs, and communication status.
  \item Prove instrumentation with a known benign transaction. Confirm that the correct project receives the request, endpoint, and data-flow evidence.
  \item Establish a baseline for application performance and health. Monitor latency, error rate, memory, CPU, restarts, and functional-test stability.
\end{enumerate}

\subsection{Workload design and coverage}

Seeker instrumentation uses HTTP requests and executed application behavior to explore data flow. Its Data Flow Map represents observed real-time flows; it is not a static proof about paths that never execute \citep{seekerinstrumentation,seekerdataflow}. Feed the instrumented application:

\begin{itemize}
  \item normal functional and integration suites;
  \item authenticated tests for every material role and tenant boundary;
  \item API contract tests with valid and invalid objects;
  \item abuse, error, alternate-path, and boundary-value cases;
  \item manual Burp transactions for high-risk sources, sinks, and workflows;
  \item safe concurrency tests for state transitions where authorized.
\end{itemize}

Compare observed endpoints, methods, roles, and transactions with the intake inventory. An unobserved item is a coverage gap even if the project has no finding.

\subsection{Triage and Active Verification}

For each detection, inspect request context, data flow, source, transformations, sanitizer or validator, sink, code location or stack, application version, and verification status. Active Verification can generate a tailored duplicate request and tag supported detections according to the result; not every checker supports it, and a request that cannot be replayed can remain untagged \citep{seekeractive}.

\begin{warnbox}[Data-changing verification]
Active Verification can be configured to send requests that may involve data-changing operations. Enable this only when the environment, accounts, test data, and rollback controls make replay safe. Exclude sensitive routes when the risk cannot be controlled.
\end{warnbox}

Use a Seeker-verified tag as strong corroboration, not as the sole risk decision. An invalidated or untagged result requires review of checker support, tokens, application state, transaction prerequisites, and agent health. After remediation, rerun the same functional or security transaction against the instrumented fixed release and retain the resulting evidence.

\section{InsightAppSec DAST assessment procedures}

InsightAppSec is an app-centric DAST service. Scan configurations determine URLs, scope, attacks, performance, authentication, and engine choice. Publicly reachable applications can use cloud engines; internal applications can use on-premises engines that return results to the platform \citep{rapid7home,rapid7engine}.

\subsection{Application and engine preflight}

\begin{enumerate}
  \item Bind the InsightAppSec application to the business application, environment, owner, release, and approved domains.
  \item Choose an engine with verified network reachability. For cloud engines, apply the current regional allowlist only where authorized. For internal targets, select an on-premises engine group whose members have equivalent network access.
  \item Verify DNS, TLS, proxy, firewall, WAF, load balancer, rate limit, and target health. Record any control bypass or test allowlisting because it affects representativeness.
  \item Create a named scan configuration for the assessment profile. Preserve configuration version, engine group, seed URLs, scope, authentication, attack template, performance settings, and schedule.
\end{enumerate}

\subsection{Scope, API input, and authentication}

Scope must include intended domains and paths while explicitly excluding sign-out, destructive, third-party, and unsafe operations. InsightAppSec can use supported WSDL and Swagger documents to generate API calls and test parameter values; verify the exact specification format supported by the deployed product before relying on it \citep{rapid7scope}.

For authenticated testing:

\begin{enumerate}
  \item Create least-privileged, synthetic accounts for each role to be scanned.
  \item Select the documented authentication method. For complex flows, Rapid7 documents recorded macros and Selenium-based authentication options.
  \item Record only the actions required to authenticate; protect files that contain session or credential material.
  \item Configure logged-in and logged-out indicators that are stable and role-specific.
  \item Run a short validation and inspect the event log and crawl state. Confirm that authenticated-only content is reached and that the scan does not silently continue logged out \citep{rapid7auth}.
  \item Use sequences for multi-step business flows where the supported feature is required; seed the environment with reversible test data.
\end{enumerate}

\subsection{Crawl, attack, and monitoring}

Attack templates are preconfigured combinations of attacks and performance options; custom templates can refine behavior \citep{rapid7templates}. Select attacks from the threat model, not by habit. Begin with a crawl-oriented validation, compare the map with the route and API inventory, then run attacks within the approved load envelope.

During execution, monitor authentication state, requests, target health, errors, timeouts, WAF actions, queue depth, rate limits, account locks, and unintended transactions. Stop when a defined threshold is crossed. A completed scan with repeated authentication, network, or target errors is not acceptable evidence.

\subsection{Review and retest}

Review attack variance, the original value, request and response snapshots, application behavior, and reproduction context. Use attack replay for controlled validation when available \citep{rapid7review,rapid7retest}. A validation scan can classify the prior observation as found, not found, or unknown; Rapid7 documents that unknown means the engine could not repeat the original attack and leaves the status unchanged \citep{rapid7scan}. Therefore:

\begin{itemize}
  \item \status{Found}: retain as open and update current evidence.
  \item \status{Not found}: corroborate the fixed release and relevant coverage before closure.
  \item \status{Unknown}: investigate reachability, state, authentication, and configuration; do not call it remediated.
\end{itemize}

InsightAppSec's API can support application onboarding, scan automation, result retrieval, and reporting. Use a least-privileged key, the current regional base URL, pagination, rate-limit handling, immutable raw capture, and an auditable service identity \citep{rapid7api}.

\section{Burp Suite manual assessment procedures}

Burp Suite Professional is the analyst-controlled layer for mapping, hypothesis testing, reproduction, and business-logic analysis. Proxy intercepts and modifies browser traffic; Target organizes scope and site-map evidence; Repeater resends controlled HTTP or WebSocket messages; Intruder automates bounded parameterized requests; Scanner supplements manual testing; Collaborator observes authorized out-of-band interactions; Sequencer analyzes token randomness; and DOM Invader assists with client-side source and sink analysis \citep{burptools,burpproxy,burprepeater,burpintruder,burpcollaborator,burpsequencer,burpdom,burpscanner}.

\subsection{Safe project setup}

\begin{enumerate}
  \item Create an encrypted project file in an approved evidence location. Record Burp version, edition, extensions, browser, proxy listener, CA handling, project configuration, and assessment identifier.
  \item Enter the exact authorized target scope. Configure out-of-scope request handling to drop unintended traffic where practical; PortSwigger documents target and out-of-scope behavior as project settings \citep{burpscope}.
  \item Disable or constrain automatic live tasks until their traffic is understood. Configure resource pools, concurrency, delays, retries, and maximum requests to match the rules of engagement.
  \item Use synthetic accounts, tenant data, and transactions. Protect session tokens, credentials, message bodies, project backups, Collaborator records, and reports as assessment evidence.
  \item Review extensions before installation for source, maintainer, permissions, network behavior, update path, and data handling. Record approved version and purpose.
\end{enumerate}

\subsection{Mapping and analysis workflow}

\begin{enumerate}
  \item Browse each supported role through normal workflows using Proxy. Preserve representative requests in Organizer or named Repeater groups.
  \item Compare the Target site map with documented routes, API specifications, client code, InsightAppSec crawl, Seeker endpoints, and server telemetry.
  \item Mark high-risk functions: identity changes, payments, exports, file operations, administration, cross-tenant objects, callbacks, asynchronous jobs, and downstream integrations.
  \item Build an authorization matrix of role, tenant, object owner, operation, expected response, and observed result.
  \item Use Repeater to alter one security-relevant variable at a time, retain the control request, and compare status, headers, body, timing, side effects, and audit events.
  \item Use Intruder only for a bounded hypothesis with an explicit payload count and request rate. Stop on account lockout, performance degradation, unexpected state change, or monitoring alert.
  \item Use Scanner on selected in-scope hosts or messages to complement, not replace, manual analysis. Review insertion points, event log, audit log, and exclusions.
\end{enumerate}

\subsection{Correlation rules}

\begin{enumerate}
  \item Generate a candidate match using application, release, weakness class, source/sink or endpoint/parameter, component/advisory, and access context.
  \item Require analyst confirmation that observations share the same root cause and remediation. CWE equality alone is insufficient.
  \item Preserve one-to-many relationships: one source defect may affect many routes; one deployed behavior may result from several defects; one package advisory may appear in several services.
  \item Choose a primary finding and attach all native observations. Do not close source observations merely because a correlation exists.
  \item Propagate remediation only after each affected version and layer is verified. Record partial fixes explicitly.
\end{enumerate}

Assign an internal remediation priority through a documented decision table that combines technical severity, exposure, business impact, exploit evidence, confidence, and control strength. The result is a workflow decision, not a modified CVSS score.

\subsection{Recommended state model}

\begin{description}[style=nextline,leftmargin=1.35in,labelwidth=1.2in]
  \item[\status{New}] Imported or reported; ownership and evidence not yet reviewed.
  \item[\status{Under review}] Analyst is validating scope, evidence, classification, and correlation.
  \item[\status{Confirmed}] Evidence supports a security weakness in the assessed version.
  \item[\status{False positive}] Evidence shows the reported condition is not present; rationale and approver required.
  \item[\status{Duplicate}] Linked to a primary finding with the same root cause; native observation retained.
  \item[\status{Accepted risk}] Authorized owner accepts defined residual risk through an expiring exception.
  \item[\status{Mitigated}] A compensating control reduces risk but the root weakness remains.
  \item[\status{Remediated}] A change is implemented; closure still requires the defined verification.
  \item[\status{Retest pending}] Correct version and environment await independent verification.
  \item[\status{Closed}] Verification passed or an approved disposition satisfies closure policy.
\end{description}

Every confirmed finding must be reproducible by an authorized reviewer without exposing unnecessary sensitive data.

\section{Remediation and verification}

Remediation changes code, configuration, dependency, credential, architecture, or operation. Verification proves that the relevant weakness no longer produces the prohibited behavior in the fixed version and that the change did not create a regression.

\toprule
\textbf{Finding source} & \textbf{Minimum verification} & \textbf{Closure evidence} \\
\midrule
\endfirsthead

\textbf{Finding source} & \textbf{Minimum verification} & \textbf{Closure evidence} \\
\midrule

Dependency & Update manifest/lock or deployed component, rebuild, test, and refresh graph/submission & Patched version in source and artifact, advisory state, SBOM or inventory, CI result \\

\begin{decisionbox}[Closure rule]
A code change, merged pull request, tool status change, or developer assertion is not independently sufficient. Close only when the designated verifier confirms the fixed version, equivalent or stronger coverage, expected secure behavior, and regression results.
\end{decisionbox}

\section{Reporting}

\subsection{Executive report}

The executive view communicates business exposure and decisions, not raw scanner volume. Include assessment scope, confidence, material risks, affected business capabilities, systemic root causes, risk trend, remediation progress, exceptions, overdue priorities, and decisions required. State limitations prominently.

\subsection{Engineering report}

The engineering view includes the architecture and coverage model, findings, code/runtime/interface evidence, root cause, affected variants, owners, remediation patterns, target releases, and retest status. Group recurring weaknesses to enable shared fixes without hiding individual affected assets.

\subsection{Assessment record}

The audit record contains authorization, targets, exclusions, commits/releases, tool versions, entitlements, configurations, scan and analysis identifiers, timestamps, accounts/roles, coverage, failures, stop events, evidence locations, decisions, approvals, and integrity controls.

\subsection{Required report limitations}

At minimum, state unsupported technologies, failed or partial analyses, unauthenticated or unstable scans, untested roles, missing test data, unreachable routes, unavailable source, environmental differences, blocked egress, disabled attacks, time-box constraints, and reliance on owner assertions. ``No critical findings'' must never be rendered as ``the application is secure.''

\subsection{Stop conditions}

Pause testing immediately on unexpected production access, customer data exposure, service degradation above the approved threshold, account lockouts beyond test accounts, irreversible transactions, alerting that indicates incident confusion, uncontrolled outbound interaction, evidence-system compromise, or scope ambiguity. Preserve the minimum evidence needed, notify the named contact, and resume only after recorded authorization.
